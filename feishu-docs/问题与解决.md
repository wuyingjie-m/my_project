# 问题与解决

## 第一篇：dashboard 三轮优化——问题与解决（9/18-9/20）

记录 2026-09-18 至 2026-09-20 对 openclaw-bot-review-furnace（openclaw-bot-dashboard）的三轮修改与优化中遇到的问题、根因定位过程、解决方法及涉及技术的详解。

## 一、应用架构与数据链路（背景）

- 应用：`/data/opt/OpenClaw-bot-review-furnace`，Next.js 16（App Router），生产模式，由 systemd 服务 `openclaw-bot-review.service` 托管，监听 `127.0.0.1:3000`。
- 数据特点：**全部读服务器本地文件和 SQLite 数据库，不调用 OpenClaw API**。
- 数据链路：

  1. 扫描 `/data/agent/`（环境变量 `OPENCLAW_INSTANCES_DIR`）发现所有实例，每个实例以 `<实例>/.openclaw/openclaw.json` 为身份配置；
  2. 每个 agent 的统计与状态：`<实例>/.openclaw/agents/<agentId>/agent/openclaw-agent.sqlite`；
  3. 定时任务：`<实例>/.openclaw/state/openclaw.sqlite` 的 `cron_jobs` 表；
  4. agent 名字/emoji：workspace 的 `IDENTITY.md` → `agent.json` → `openclaw.json` 逐级回退。
- 关键接口：`/api/config`（机器人卡片）、`/api/stats-all`（消息统计）、`/api/agent-status`（在线状态）、`/api/agent-activity`（任务追踪/今日播报数据源）。

## 二、问题一：今日播报板块与定时任务脱节（9/18）

**问题**：今日播报页的"已完成/进行中/待开始"三个统计卡读取的是记忆 Markdown 文件里的 checkbox 待办，与定时任务无关；下方记录也不展示失败任务。

**解决**：

1. 重写 `app/daily/page.tsx`：数据源改为 `/api/agent-activity?includeInstances=1` 返回的 `cronJobs`（与总览页"Agent 任务追踪"同源），按互斥口径聚合：

   - 已完成 = 今天成功收尾（`lastStatus === 'success'` 且 `lastRunAt` 在今天）
   - 进行中 = `isRunning === true`
   - 待开始 = 今天还没执行且未在运行
   - 今日记录 = 今天失败（`lastStatus === 'failed'` 且失败时间在今天）的任务清单（任务名、所属 Agent/实例、时间、错误摘要、连续失败次数）
2. `/api/agent-activity` 的 `CronJobInfo` 补充 `enabled` 字段透传，停用任务不计入统计。
3. 页面 30 秒自动刷新；i18n 补繁中/简中/英文三语言文案。

## 三、问题二：点刷新要几分钟才更新（9/18）

### 3.1 症状

浏览器刷新 / 页面刷新按钮，都要等待数分钟。四个数据接口实测全部超时无响应（`HTTP 000`），连静态页面也无法返回。

### 3.2 根因（三层叠加）

**根因 1：每次请求都全量重算。**`/api/config` 与 `/api/stats-all` 没有有效缓存（stats-all 存在"缓存只写不读"的缺陷——`statsCache` 只有赋值语句没有读取分支），每次请求都要重新遍历 8 个实例、32 个 agent。

**根因 2：重算方式同步阻塞事件循环。** 统计库读取用 `execFileSync` 同步 spawn `sqlite3` 命令行进程，每个 agent 两次查询，其中一次全量转储 `transcript_events` 表（`SELECT ... ORDER BY created_at ASC`，单 agent 导出最大 21MB JSON）。32 个 agent 串行同步执行，期间 Node.js 事件循环完全冻结，整个服务对任何请求（包括静态页面）都无响应。

**根因 3：轮询堆积导致进程"睡死"。** 页面每 30 秒自动轮询，计算未完成新请求又进来。堆积后进程进入异常状态：进程存活、CPU 仅 1.8%、文件描述符仅 112/52 万（排除了句柄耗尽）、主线程 `WCHAN=ep_poll`（空闲睡眠），但内核层 `ss` 显示 LISTEN 队列 `Recv-Q` 积压 43 个连接不被 accept——事件循环既不干活也不再接受新连接。

### 3.3 解决方法

1. **SWR 缓存 + 单飞去重**：四个重接口全部改造（详见 5.1/5.2）。
2. **磁盘持久化**：新增 `lib/disk-cache.ts`，计算成功后把响应落盘到 `.api-cache/<接口名>.json`，服务重启时模块加载即恢复——彻底消除重启后的冷启动等待。
3. **node:sqlite 进程内查询**：`lib/sqlite-stats.ts` 从 spawn `sqlite3` CLI 改为 Node 24 内置 `DatabaseSync`（详见 5.4）。
4. **每 agent 统计缓存**：`getSqliteAgentStats` 加模块级 Map 缓存（TTL 5 分钟），config/stats-all/models 三个路由共享，避免同一 DB 在 TTL 内被反复查询。
5. **尾部读取**：agent-activity 的转录文件只读末尾（cron 转录 256KB、父会话 512KB、子会话事件 128KB），并新增 `readTextTail` 工具函数（详见 5.6）；父会话扫描上限 `MAX_PARENT_SESSIONS_TO_PARSE` 从 40 降到 12。
6. **事件循环吞吐**：服务启动注入 `UV_THREADPOOL_SIZE=16`（libuv 线程池默认 4，异步 fs/DNS 共用，加大余量）。

### 3.4 优化效果

- 日常刷新：分钟级 → **内存缓存 \~3ms**
- 冷计算：config 0.26s、stats-all 1.73s（修复前 60s+ 超时无法完成）
- 并发风暴测试（10 并发 × 4 接口共 20 请求）：最慢 2.4s，全部 200

## 四、问题三：统计全丢、日期停在 9/7（9/20 回归）

### 4.1 症状

优化后刷新确实变快了，但统计信息全没了：机器人卡片的会话数/消息数/token 用量/平均响应缺失，任务追踪为空，消息统计最新日期停在 9/7（服务器迁移日）。

### 4.2 根因（三个叠加）

**根因 1：systemd 服务环境变量指向错误实例。** 服务由 `systemd` 管理（`Restart=always`），9/18 手动杀进程优化重启时，systemd 按其配置自动拉起了服务，而配置里 `OPENCLAW_HOME=/data/agent/openclaw_TeamS/.openclaw`——之后所有接口都在给 TeamS 实例取数：config 顶层只剩 TeamS 的 3 个 agent、任务追踪为空。当时还伴随手动进程与 systemd 进程竞争 3000 端口的 `EADDRINUSE`（详见 5.7）。

**根因 2：时间窗 SQL 少了括号。** 9/18 加 120 天统计窗口时写成 `WHERE (typeof created_at = 'integer' AND ...)`——SQLite 的 `typeof` 是函数，**必须带括号**，不带括号直接报 `syntax error near "created_at"`。于是所有 agent 的统计查询全部静默抛异常 → `getSqliteAgentStats` 返回 null → 代码回退去读迁移前的旧 JSONL 会话文件 → 旧文件数据止于 9/7（迁移日）。这就是"日期停在 9/7"的完整解释。

**根因 3：任务追踪的缓存包装 bug。** 9/18 给 agent-activity 加 SWR 缓存时，`collectAgentActivity` 返回的是 `NextResponse.json({agents})` 响应对象而非纯数据，缓存层把这个 Response 对象 JSON 序列化后存起来——任务追踪接口从此永远返回空壳。

### 4.3 修复

1. `typeof created_at` → `typeof(created_at)`（SQL 先拷贝 DB 副本到 /tmp 验证通过再上线）。
2. systemd 环境变量修正并 `daemon-reload` + `systemctl restart`（后期按业务确认，主实例归属最终归位 `openclaw_TeamS`——小龙虾工作台视角，`openclaw_sxs` 等作为子实例分组展示）。
3. `collectAgentActivity` 改为返回纯数据 `{ agents }`，缓存层与 HTTP 层各司其职。

### 4.4 修复后验证

- 主实例分组：main / data_group / rival，3/3 有真实统计（归位 TeamS 后）
- 全实例：26 个 agent、108 个定时任务全覆盖
- 消息统计：41 天连续非零，最新到当天（9/20 当天 1.33 亿 tokens）
- 机器人卡片：24 个实例内 agent 中 23 个有真实 token 数据（如 GTM/main 1.83 亿、GYL/main 8576 万）

## 五、技术详解

### 5.1 SWR（Stale-While-Revalidate）缓存架构

SWR 即"先返回旧数据（Stale），同时后台重新验证刷新（Revalidate）"，源自 HTTP 缓存标准策略。落到每个重接口：

```
请求进来
 ├─ 内存缓存存在且未过期 → 直接返回（毫秒级）
 ├─ 缓存存在但已过期 → 立即返回旧数据
 │    同时：若无其他重算在进行 → 启动 1 个后台任务重算
 │      完成后：更新内存缓存 + 写磁盘缓存
 └─ 无缓存（冷启动且无磁盘缓存）→ 同步计算一次
```

关键点：**重算是"请求触发、按需"的，不是定时器定时跑**——没人访问时后台完全安静，不做无谓计算。

### 5.2 单飞去重（single-flight）

用模块级标志位保证**同一时刻最多一个重算任务**：

```ts
let activityRecomputing = false;
let activityRecomputeStartedAt = 0;
const ACTIVITY_HARD_BUDGET_MS = 180_000;

// 过期时的处理
const stuck = activityRecomputing
  && Date.now() - activityRecomputeStartedAt > ACTIVITY_HARD_BUDGET_MS;
if (!activityRecomputing || stuck) {
  activityRecomputing = true;
  activityRecomputeStartedAt = Date.now();
  collectAgentActivity(request)
    .then((data) => { activityCache = { data, ts: Date.now() }; saveDiskCache(...); })
    .catch((err) => console.error('background refresh failed:', err))
    .finally(() => { activityRecomputing = false; });
}
return NextResponse.json(cached.data);   // 无论是否重算，立即返回旧数据
```

`stuck` 兜底：若某次重算异常挂起超过 180 秒硬预算，允许重新调度，避免标志位永久卡死。这一个机制从原理上杜绝了"轮询堆积 → 进程压死"的旧病。

### 5.3 事件循环阻塞与 execFileSync

Node.js 是单线程事件循环模型：所有 JS 执行与网络 IO 复用主线程。`execFileSync` 会同步 spawn 子进程并阻塞主线程直至子进程退出（阻塞点在 `waitpid`），期间**事件循环无法 accept 新连接、无法处理任何已连接请求**——这就是"计算几分钟、服务无响应几分钟"的机制。

排查睡死进程的三个关键证据：

- `ps -o stat,wchan` → `S` / `ep_poll`（主线程空闲睡眠而非卡在系统调用）
- `ss -tlnp` → LISTEN 队列 `Recv-Q 43`（内核已排队、应用不 accept）
- `/proc/<pid>/limits` 与 `fd 计数` → 排除文件描述符耗尽（112/524288）

### 5.4 node:sqlite（DatabaseSync）进程内查询

Node 24 内置 `node:sqlite` 模块，把"spawn sqlite3 CLI + JSON 序列化导出 + JSON.parse"（进程创建开销 + 21MB 字符串解析，秒级）替换为进程内直接读库（毫秒级）：

```ts
import { DatabaseSync } from "node:sqlite";

const db = new DatabaseSync(dbPath, { readOnly: true });
try {
  db.exec("PRAGMA busy_timeout = 5000");   // 网关持续写库，读冲突时等锁最多 5 秒
  const sessionRow = db.prepare(
    "SELECT COUNT(*) AS sessionCount, MAX(COALESCE(last_activity_at,last_interaction_at,updated_at)) AS lastActive FROM session_nodes"
  ).get();
  const eventRows = db.prepare(
    "SELECT session_id, created_at, event_json FROM transcript_events "
      + "WHERE (typeof(created_at) = 'integer' AND created_at >= ?) "
      + "OR (typeof(created_at) = 'text' AND created_at >= ?) "
      + "ORDER BY created_at ASC"
  ).all(cutoffMs, cutoffIso);              // 参数绑定，避免拼接/类型问题
  // ...原有聚合逻辑不变（遍历 eventRows 提取 usage tokens/响应时间/模型分布）
} finally {
  db.close();
}
```

要点：`readOnly: true` 只读打开；`PRAGMA busy_timeout` 让锁冲突时等待而非立即报错；参数绑定 `?` 避免 SQL 注入与类型歧义；`finally` 确保 db.close()。

### 5.5 SQLite 相关表结构

**agent 私有库**`agents/<agentId>/agent/openclaw-agent.sqlite`（每 agent 一个）：

- `session_nodes`：会话列表（id、状态、`last_activity_at` 最近活跃）
- `transcript_events`：完整对话转录，每条消息一行——`session_id`、`created_at`（integer 毫秒时间戳）、`event_json`（消息全文 JSON：角色、文本、工具调用、usage tokens、stopReason、模型名）。统计聚合的数据源。

**实例级共享库**`<实例>/.openclaw/state/openclaw.sqlite`（每实例一个）：

- `cron_jobs`：定时任务注册表——任务定义（`name`、`payload_kind`、`enabled`）+ 运行状态（`state_json` 内含 `nextRunAtMs`、`lastRunAtMs`、`lastStatus`、`consecutiveErrors`），`owner_agent_id` 区分归属。
- `audit_events`：网关审计事件。

### 5.6 尾部读取算法（readTextTail）

任务追踪只需要"最近发生了什么"，但会话转录文件可能很大。尾部读取：`stat` 取文件大小 → `fs.open` + 定位 `offset = size - maxBytes` 读取末尾 N 字节 → 转 utf8 后丢弃第一个可能被截断的半行。按场景配额：cron 转录 256KB、父会话 512KB、子会话事件 128KB。单文件读取从全量 MB 级降为固定 KB 级。

### 5.7 systemd Restart=always 与端口竞争

服务配置 `Restart=always, RestartSec=5`：手动 `kill` 进程后 5 秒即被 systemd 自动拉起。9/18 手动 `nohup` 启动新进程时与 systemd 拉起的进程竞争 3000 端口，出现 `EADDRINUSE: address already in use`——日志里"启动失败"的进程是手动那个，真正对外服务的一直是 systemd 拉起的。**正确姿势：托管在 systemd 下的服务一律用 `systemctl restart` 操作，不要手动 kill + nohup。** 同时注意 `npm run start --hostname ...` 的参数不会透传给脚本（要用 `-- ` 分隔或直接调用 `./node_modules/.bin/next start -H ... -p ...`），否则日志报 "Invalid project directory"。

### 5.8 其他踩坑记录

- **pkill 自匹配陷阱**：`pkill -f "next start"` 会匹配到承载命令本身的 `bash -c` 进程（命令行文本里含关键词），把自己杀掉导致命令中断。杀服务应从 `ss -tlnp` 解析 PID 后精确 `kill`；睡死进程对 SIGTERM 无响应需 `kill -9`。
- **会话存储格式变迁**：新版 OpenClaw 会话写入 sqlite（`transcript_events`），不再产生 `.jsonl` 文件——验证数据时要查库而不是 grep 文件；旧 agent 迁移时带来的 `.jsonl` 是 9/7 前的历史数据，这也解释了"回退读取时日期停在 9/7"。
- **exec 安全护栏**：OpenClaw agent 环境下禁止直接用 sqlite3 打开 `OPENCLAW_STATE_DIR` 下的数据库，验证 SQL 需先 `cp` 副本到 /tmp 再测。
- **markdown 转义**：飞书文档 markdown 写入时字面 `<` 需转义为 `\<`；代码块内无需转义。

## 六、遗留问题

- QD / TeamS 实例在 config 的 instances 分组中缺失：日志报 `Invalid regular expression: /(?<=\n)/: Stack overflow`（来自依赖库编译 lookbehind 正则时的 V8 已知栈溢出问题），agent 卡片数据不受影响（24 个实例内 agent 均正常），后续定位依赖库后处理。
- 统计的生命周期总量（totalTokens 等）现基于近 120 天事件窗口，对看板展示无实质影响。

# 第二篇：播报强制化——从纪律约束到网关插件硬门禁（9/20-9/21）

## 一、问题：写入 AGENTS.md 的播报规则"不够硬"

### 1.1 背景

9/16-9/17 确立了"凡调用工具的任务必发过程播报"制度（长任务执行中 agent 要通过 lark-cli 以 bot 身份向当前会话窗口发一行进展），并将规则写入全部 8 个实例、28 份 AGENTS.md（9/20 完成同步）。AGENTS.md 是 OpenClaw 的 bootstrap 上下文文件，会在每个 run 启动时注入 system prompt——理论上模型每次执行任务都"读过"规则。

### 1.2 两轮核查证伪了纪律层的可靠性

对 28 个 agent 做了两轮"工具调用数 vs 播报调用数"对比核查（数据源：各 agent 私有库 `transcript_events` 表，关键词匹配播报调用特征 `+messages-send`）：

- 第一轮（9/18 12:00-9/20 14:00）：16 个有工具调用的 agent 中 8 个执行了播报、8 个零播报
- 第二轮（9/20 14:00-9/21 09:46）：15 个有工具调用的 agent 中 7 个执行、8 个零播报，执行率约 47%-50% 持平
- 更关键的发现是"优等生退步"：TeamS/data_group（上轮 29 条播报 → 本轮 0）、QD/mlx（7 → 0）、GYL/main（3 → 0）——**上一轮执行得很好的 agent，下一轮也会归零**

### 1.3 结论

纪律层（规则写入 system prompt）是**软约束**：规则能否被遵守取决于模型在长任务连续工具调用流中的注意力分配，没有强制力，执行率天然波动。要让"每次执行长任务时都能播报"成为保证，必须在**模型之外的执行层**做硬卡点。

## 二、方案选型：OpenClaw 的三层机制对比

OpenClaw 有三套完全不同能力的机制：

| 层 | 能力 | 为什么行/不行 |
|-|-|-|
| 纪律层（AGENTS.md/LEARNINGS） | 提醒 | 两轮核查证伪：执行率 \~50% 且波动 |
| 内部 hooks（HOOK.md 目录钩子） | 只能做生命周期/命令事件的**事后副作用**（记日志、注入上下文），不能拦截工具调用 | 做审计可以，做卡点不行 |
| **插件 hooks（`api.on(...)`）** | 类型化钩子运行在 agent loop 和 Gateway 管线内部，`before_tool_call` 可以 **block 工具调用、改写参数、要求审批** | 唯一能做硬卡点的层 |

被否决的替代方案：`before_tool_call` 还支持 requireApproval（挂起等待人工审批）——但那等于把人变成门禁本身，每个工具调用都要人点头，体验最差，不选。

## 三、OpenClaw 网关原理与 agent 执行过程（信息流 转）

### 3.1 网关是什么

每个 OpenClaw 实例一个网关进程（`openclaw-gateway`），它是该实例一切的宿主：

- 所有 agent 的运行时（agent loop 在网关进程内执行）
- 渠道连接（飞书 WebSocket 长连接、Telegram 等）
- 定时任务调度器（cron_jobs）
- 插件宿主（插件代码作为模块加载进网关进程，trusted，拥有文件系统权限）

每实例监听独立端口（本机 18789-18797 区间：GTM=18794、TeamS=18793、sxs=18796、QD=18798 等）。飞书消息通过长连接到达网关，不需要开放入站端口。

### 3.2 一次任务的完整执行过程（以真实案例流转）

以 GTM 实例 cqy-bot 在飞书群收到一条消息为例（网关日志实录）：

```
飞书服务器
   │  (飞书 WebSocket 长连接推送事件)
   ▼
openclaw-gateway 进程 [feishu 渠道插件]
   │  日志: message in group oc_xxx
   │  日志: dispatching to agent (session=agent:cqy:feishu:group:oc_xxx)
   ▼
会话装配（session load）
   │  读取会话转录（sqlite: transcript_events）
   │  注入 bootstrap 上下文 ←★ AGENTS.md/SOUL.md 就是这里进入 system prompt 的
   ▼
Prompt 组装
   │  system prompt = OpenClaw 基础提示 + skills + bootstrap 上下文 + per-run 覆盖
   ▼
┌─ agent loop（核心循环，下述步骤循环直到模型停止）──────────┐
│  1. LLM 调用：provider-transport-fetch → 模型 API          │
│     （日志: model=GLM-5.3-flash status=200）                │
│  2. 模型返回 assistant 消息：                               │
│     - 纯文本 → 循环结束（stopReason=stop）                  │
│     - 带 toolCall → 进入第 3 步                             │
│  3. ★ before_tool_call 钩子触发（插件拦截点在这里）★        │
│  4. 网关执行工具（exec/read/...）→ toolResult               │
│  5. toolResult 追加进上下文 → 回到第 1 步                   │
└────────────────────────────────────────────────────────┘
   ▼
交付（delivery）：assistant 文本经渠道插件发回飞书
   ▼
全程事件流式写入 transcript_events ←★ dashboard 统计的数据源
```

关键认知：**AGENTS.md 的播报规则只是 system prompt 的一部分**——它在第 2 步"装配"时进入模型视野，但模型在长任务的几十次工具调用中是否每次都记得执行播报，没有任何机制保证。插件门禁则作用在第 3 步——模型**请求**调工具和网关**实际执行**工具之间，是执行层的强制检查点。

### 3.3 before_tool_call 的契约与信息流转

- 注册方式：`api.on("before_tool_call", handler)`，handler 为**同步函数**（部分钩子的 async 返回值不被采纳）
- 入参：`event`（含 `toolName`、`params`、`runId` 等）+ `ctx`（含 `agentId`、`sessionKey`、`runId` 等；文档明确这些字段在部分触发路径可能缺失，handler 必须防御式判断）
- 返回：`{ block: true, blockReason: "..." }` 为终态——本次工具调用不执行，`blockReason` 文本**作为工具执行错误注入模型上下文**；`{ block: false }` 为 no-op
- 优先级：`{ block: true }` 会停止低优先级 handler

**弹回式门禁的自愈闭环**（不需要任何人工参与）：

```
模型调工具 → 门禁检测到未播报 → {block:true, blockReason:"先播报再重试"}
   ↓
模型收到"工具执行失败"，错误信息就是补救指引
   ↓
模型执行播报（lark-cli messages-send）→ 门禁识别为播报调用 → 放行并记录状态
   ↓
模型重试原工具调用 → 通过 → 任务继续
```

门禁不需要判断模型"心里有没有意识到"，只看状态机（本 run 是否出现过播报调用）；模型的自我纠错由 blockReason 文本驱动。

### 3.4 sessionKey 与豁免判定

`ctx.sessionKey` 的结构即豁免判定的依据：

- 交互会话：`agent:<agentId>:feishu:group:<chatId>` / `agent:<agentId>:feishu:direct:<openId>` —— **门禁对象**
- cron 触发：`agent:<agentId>:cron:<jobId>` —— 豁免（无人实时观看，完成时自带投递）
- 后台子代理：`agent:<parent>:subagent:<uuid>` —— 豁免
- 心跳：sessionKey 含 heartbeat —— 豁免

防御式原则：`ctx.sessionKey` 或 `ctx.runId` 缺失时放行不门禁（宁可漏拦，不可误拦正常任务）。

## 四、插件实现（broadcast-gate）

### 4.1 三件套结构

- `package.json`：`{"name":"broadcast-gate","type":"module","openclaw":{"extensions":["./index.js"]}}`
- `openclaw.plugin.json`：manifest（id、activation.onStartup、configSchema——mode: log|enforce、staleMinutes、logFile）
- `index.js`：门禁逻辑（约 100 行）

注意：`before_tool_call` 不需要 `plugins.entries.<id>.hooks.allowConversationAccess` 权限（那是对话类钩子的门槛）。

### 4.2 状态机与规则

按 `runId` 在插件进程内维护 Map 状态（网关重启清零，run 生命周期短可接受）：

```js
// 播报调用自识别：exec 且参数是「以 bot 身份调 lark-cli 播报」（AGENTS.md 标准形态）
if (isBroadcastCall(event)) {
  st.broadcasted = true; st.lastBroadcastAt = now;
  return;                                   // 放行
}
if (!st.broadcasted && fresh)
  reason = "PROGRESS_BROADCAST_REQUIRED";   // 规则1：本轮首个工具调用前未播报
else if (st.broadcasted && now - st.lastBroadcastAt > staleMs)
  reason = "MILESTONE_STALE";               // 规则2：播报后静默超 5 分钟
else if (!st.broadcasted && !fresh && now - st.firstToolAt > staleMs)
  reason = "PROGRESS_BROADCAST_REQUIRED";   // 规则2b：始终未播报且已超阈值
```

- 规则 1 弹回后若模型仍不播报，不持续弹（防死循环卡死任务），由规则 2b 在 5 分钟阈值后再次弹回——与用户拍板的"5 分钟弹一次补播报"一致
- mode: `"log"`（只记违规日志不拦截，试跑观察）/ `"enforce"`（真弹回），通过 `api.pluginConfig` 读取，配置变更热重载切换
- 每次弹回写一行 `broadcast-violations.log`（审计抽查文件）

### 4.3 安装与配置

```bash
openclaw plugins install --link <插件目录> --force --accept-capabilities
openclaw plugins enable broadcast-gate
```

openclaw.json 配置（**注意嵌套位置**：插件配置必须在 `entries.<id>.config` 下，直接平铺在 `<id>` 下会被 schema 校验拒绝 `Unrecognized keys`）：

```json
{
  "plugins": {
    "entries": {
      "broadcast-gate": {
        "enabled": true,
        "config": {
          "mode": "enforce",
          "staleMinutes": 5,
          "logFile": "/data/agent/openclaw_GTM/.openclaw/logs/broadcast-violations.log"
        }
      }
    }
  }
}
```

`before_tool_call` 不需要 `hooks.allowConversationAccess`。安装时因插件声明了工具拦截能力，需 `--accept-capabilities` 显式同意。

## 五、部署过程与踩坑（GTM + TeamS 实录）

1. **安装被能力同意拦截**：首次 install 报 `requires capability consent`——工具拦截属于需显式同意的能力，加 `--accept-capabilities` 重跑成功。

# 第三篇：架构与技术原理——网关、执行模型、长连接、权限隔离（9/21）

本篇整理 9/21 下午讨论的架构概念与技术原理，均结合本服务器（8 实例）的真实情况。

## 一、插件与 AGENTS.md 的加载机制——用户需要重启会话吗？

**答案：不需要。两者加载链路完全独立，对用户透明。**

### 插件（broadcast-gate）——网关进程内，运维层动作

- 插件代码作为模块**加载进网关进程**，对本实例**所有 agent 的所有工具调用**自动生效
- 部署时的网关重启是**运维层一次性动作**；此后用户正常聊天，门禁自动工作
- 插件**配置变更**（log ↔ enforce 切换、阈值调整）走配置热重载，无需重启
- 唯一需要重启的场景：改插件源码本身（index.js）——已完成

### AGENTS.md——每个 run 启动时自动注入

- AGENTS.md 属于 bootstrap 上下文，注入时机是**每个 run 启动时的 bootstrap 阶段**（一个 run = 用户一条消息触发的任务执行）
- 文件每个 run 都重新解析——**改了 AGENTS.md，该 agent 的下一条消息就会带上新规则**，无需发 /new、无需重启
- 实证：门禁部署后产生的 17 条真实弹回记录（sxs 拦 wyj 3 次、GTM/main 被弹多次、TeamS/main 被弹 3 次）全部发生在普通聊天过程中，没有任何人重启过会话

补充：如果某个 agent 的行为没反映 AGENTS.md 最新规则，让它发 /new 清一下旧上下文——这解决的是"旧上下文残留干扰"，与加载机制无关。

## 二、agent 状态判定链路——fqc"显示离线但能工作"的完整解释

### 现象

dashboard 显示 openclaw_XMT 的 fqc 离线，但 fqc 实际能正常执行任务。

### 状态判定原理

dashboard（agent-status 接口）判定 agent 状态的第一步是 **gatewayOk**：对实例配置文件（openclaw.json）中记录的 gateway.port 做 **TCP 探测**——探测失败直接判定 offline，后续的活跃度判断（working/online/idle）根本不会进行。

### 为什么 fqc 实际能工作

agent 收发飞书消息走的是 **WebSocket 出站长连接**（网关主动连出去到飞书服务器），与网关的**入站管理端口**是两条完全独立的链路。入站端口探测失败只影响 dashboard 的显示，不影响收发消息。

### 根因链（配置漂移）

1. 9/21 修 XMT 端口冲突时，XMT 配置的 gateway.port 从 18797 改为 18798（原 18797 与 sxs 网关实际端口冲突）
2. 14:03:51，XMT 网关被 **config watcher 自动重启**（触发：修插件布局时 install --link 更新了 openclaw.json，文件 mtime 变更被检测）——拉起的新网关进程读到的配置端口是 **18796**（12:06-14:03 间配置曾被还原，还原来源未完全查明，疑似网关配置持久化或 ops 体系端口记录）
3. 新网关监听 **18796**，而 dashboard 按配置探测 **18798** → Connection refused → fqc 显示 offline
4. **修复**：将 XMT 配置的 gateway.port 对齐到网关实际监听的 **18796** → fqc 恢复正常显示（idle 空闲态——它最近确实没有会话活动，不是故障）

### 排查方法论

- "显示离线但实际能用"：先看 agent-status 返回的 **gatewayOk 字段**（false = 网关端口探测失败），再对齐配置与实际监听
- 端口归属的可靠确认方式：**ss -tlnp 按端口反查 pid**，再 readlink /proc//cwd 确认进程工作目录（注意 grep "pid=xxx " 带尾随空格会匹配失败，应按端口 grep 后提取 pid）
- 进程的 /proc//environ 是启动环境的铁证（可用于确认进程读的是哪份配置）；/proc//fd/1 可确认日志输出流向

## 三、权限模型：root 运行身份与实例隔离

### 3.1 事实核查（当时的服务器状态）

- 全部实例文件属主：**root:root**（含 openclaw_sxs——所谓 sxs_leader 用户当时并不存在）
- wyj 的 exec 身份：**uid=0(root) gid=0(root)**
- 全部 8 个网关进程：**root 运行**

结论：wyj agent **已经以 uid 0 运行**，天然拥有跨实例管理权限（当天的插件全量铺开就是实证），无需任何变更。

### 3.2 概念澄清：root 用户（uid 0）与 root 组的区别

- **uid 0（以 root 用户运行）**：最高权限，绕过一切文件权限位（rwx 对 root 无效），可读写系统上任何文件
- **仅加入 root 组**：不是最高权限——只有当文件的属组是 root 且显式给了组 rwx 权限时才有对应访问权。对其他用户拥有的文件，依然只是"其他用户"
- uid 0 的边界：chattr +i 不可变文件（需先解除）、SELinux/AppArmor 策略（本机未启用针对 OpenClaw 的策略）、只读挂载——实测层面当天全部跨实例操作零权限报错

### 3.3 为什么"同一网关内做 per-agent 权限分级"做不到

**核心架构事实：一个实例的所有 agent 共享同一个网关进程，agent 没有独立进程。**

agent 的工具调用（读文件/写文件/执行命令）的实际执行者是**网关进程**，因此文件权限取决于**网关进程的 uid**，与"哪个 agent 发起的"无关：

- 网关以 root 运行（现状）：所有 agent 的工具调用都是 root——wyj 有最高权限，但其他 agent 同样有，**per-agent 隔离不成立**
- 网关以普通用户运行：**所有 agent（包括 wyj）都只有该用户权限**——wyj 反而会失去管理能力，且 wyj 自己的 root 属主文件（会话数据库等）将不可访问，wyj 会故障

因此曾设想的方案"创建 sxs_leader 用户、把实例中除 wyj 外的文件 chown 给它、wyj 文件保持 root"无法达到目的：只要网关还是 root 运行，chown 只是名义归属，OS 层无隔离效果；且该方案存在**未来风险**——若有人把网关改以 sxs_leader 运行（以为更安全），wyj 的 root 属主文件将不可访问，wyj 会第一个故障。

### 3.4 可行的两条路径

**方案 A：插件层文件 ACL（同网关内，改动小）**——扩展门禁插件的思路再写一个 file-acl 插件：before_tool_call 时检查发起 agent（ctx.agentId）+ 工具参数中的目标路径，非 wyj 的 agent 访问 wyj 的 workspace、主实例配置等敏感路径时直接 block。工具层 per-agent ACL，不依赖 OS 权限，部署管线与 broadcast-gate 完全一致。

**方案 B：实例拆分（OS 级真隔离，架构变更）**——wyj 迁出 sxs 独立成实例（root 跑），sxs 剩余 agent 的网关和文件迁移到 sxs_leader 用户。OS 层面真隔离，但涉及 wyj 迁移、凭据、dashboard 适配，是方案级变更。

### 3.5 实例级用户隔离（不同实例用不同用户启动）——原理成立，有前提有边界

**原理成立**：网关进程以哪个用户运行，该实例内所有 agent 的工具调用就以该用户身份执行文件操作（执行者就是网关进程）。即：GYL 网关以 GYL 的用户运行 → GYL 的 agent 写不了 TeamS 的 openclaw.json 和 sqlite。

**成立的 4 个前提**：

1. 网关进程真正以该用户运行（systemd unit 指定 User=，或降权启动）
2. 实例目录树文件属主同步 chown（网关对自己的 openclaw.json、state/、agents/、日志要可写，否则起不来或故障）
3. **提权通道堵住**：sudoers 无 NOPASSWD 宽松规则；用户不在 docker 组（docker 组权限 ≈ root）；无额外 setuid 二进制
4. 共享插件/脚本不含跨实例敏感信息

**诚实的边界（隔离的是文件写入，不是完全监狱）**：

- 文件系统 ✅：跨实例文件写入被 OS 拦截——核心效果成立
- 网络层共享：同机 localhost 端口互达，QD 的 agent 理论上能 curl TeamS 网关 API（需拿到 token）——文件隔离 ≠ 网络隔离
- /tmp 全机共享：粘滞位只防删除他人文件，world 可读文件互相可见
- 系统资源（CPU/内存/磁盘）不隔离，单实例可影响全局

**部署要点**：systemd unit 化（User= + Restart=always）**一举两得**——同时解决降权隔离与"网关无自愈"问题（配置变更触发的自动重启将由 systemd 正确拉起，不再出现"只关不起"的离线）。

### 3.6 实际发生的端口交叉占用案例（配置与运行脱节）

- sxs 网关（旧进程）实际监听 **18797**，但其配置文件写的是 18796（启动后配置被改过，进程未重启，产生脱节）
- XMT 配置的 gateway.port=18797 与之冲突，XMT 新网关启动即 EADDRINUSE 退出
- 修复：XMT 配置改用 18798（空闲端口）恢复服务；后为对齐网关实际监听（见 3.6 前述 fqc 排查），最终落在 18796
- 教训：**网关的配置端口与实际监听端口可能脱节**（改配置未重启），确认端口归属要用 ss -tlnp 按端口反查 pid，不要只信配置文件

## 四、网关（openclaw-gateway）详解

### 4.1 定位

网关是每个实例的**常驻守护进程**，是该实例一切的宿主：本服务器 /data/agent/ 下 8 个实例对应 8 个 openclaw-gateway 进程，各监听一个本地端口（18790-18798）作为管理入口。

### 4.2 五大职责

1. **渠道连接**：与飞书服务器维持 WebSocket 长连接（出站），接收事件推送、发送回复——agent 收发消息的生命线
2. **agent 运行时宿主**：agent loop 在网关进程内执行（LLM 调用、工具执行、插件钩子全在此进程）——agent 不是独立进程
3. **会话与状态管理**：对话历史/工具结果写入 agent 私有库的 transcript_events，会话元数据在 session_nodes
4. **定时任务调度器**：读取 state/openclaw.sqlite 的 cron_jobs 注册表，到点唤醒对应 agent 执行（如每日日报）
5. **插件宿主**：broadcast-gate 等插件作为模块加载进网关进程，在 agent loop 的各环节（工具调用前后、消息收发、生命周期）被类型化钩子调用

### 4.3 技术细节

- 进程：openclaw-gateway（Node.js），以 root 运行
- 监听：127.0.0.1:<端口> ——这是网关自己的 **WebSocket API**，供 openclaw CLI、Control UI 连接管理；飞书消息**不走**此端口（走出站长连接）
- 配置：<实例>/.openclaw/openclaw.json（端口、auth token、渠道、插件 entries）
- 启动方式（本机现状）：无 systemd unit 的孤儿进程（nohup 挂起），日志重定向到 gateway-run.log——**无自愈，被关闭即离线**

### 4.4 网关单点的三个特性（问题放大器）

1. **网关挂 = 整实例离线**（无自愈机制的部署下）
2. **配置变更触发自动重启**（config watcher）：有 supervisor 的部署是平滑升级，孤儿进程部署是"只关不起"
3. **端口即身份**：端口被占/被改，网关起不来或 dashboard 认不出

### 4.5 组件关系

```
飞书服务器 ◄──WS 长连接──► openclaw-gateway（每实例一个）
                             ├─ 渠道插件（feishu 等）
openclaw CLI / Control UI ◄──WS API──► ├─ agent 运行时（全部 agent）
                             ├─ 插件（broadcast-gate…）
dashboard ◄─直读文件/sqlite（不经网关 API）─► ├─ cron 调度器
                             └─ 写入各 agent 私有 sqlite + state/openclaw.sqlite
```

注意：dashboard（review-furnace）**不经过网关 API**，直读各实例文件与数据库——这是它能在网关故障时仍出统计数据的原因，也是它的统计数据与网关实时状态可能存在时间差的原因。

## 五、WebSocket 长连接

### 5.1 原理

WebSocket 连接从一个普通 HTTP 请求开始，携带 Upgrade: websocket 头请求**协议升级**；服务器返回 101 Switching Protocols 后，这条 TCP 连接上改跑 WebSocket 帧协议。三个关键机制：

- **帧通信**：数据切帧传输（文本帧/二进制帧/控制帧），开销仅几字节，远轻于 HTTP 头
- **全双工**：同一连接双向同时主动发送
- **心跳保活**：定期互发 ping/pong——确认对端存活 + 刷新 NAT/防火墙会话表防止超时断连

### 5.2 为什么能长连接飞书服务器（NAT 后无公网入站）

关键在**连接方向**：出站连接（由内向外发起）天然畅通——NAT/防火墙只拦外部主动进入的连接。连接建立后登记进中间设备会话表，双向数据（包括飞书推下来的消息）都走这条已建立通道；心跳持续刷新会话；断线后网关自动重连（指数退避）。**飞书从始至终不需要"找到"内网的网关。**

这也是 fqc 排查结论的架构基础：**入站管理端口故障不影响出站长连接的消息收发**。

### 5.3 本机形态

8 个网关各自维持一条到飞书的 WS 连接（实例内所有 bot/群共用）。网关重启期间连接断开，飞书消息有十几秒盲区（日志可见 ws client closed → started 循环）；OpenClaw 用去重机制（dedup warmup）应对重连期间的事件补推。

## 六、agent loop（代理循环）

### 6.1 定义与必要性

agent loop 是 agent 处理一次任务的执行引擎流程：模型思考 → 请求执行动作 → 网关执行 → 结果回流 → 再思考，循环直到完成。

**必须循环的根因**：大语言模型只会生成文本，不能执行任何操作。agent 能干活是因为模型输出可以带工具调用请求（toolCall），而真正执行工具的是网关。所以流程必然是：模型请求 → 网关执行 → 结果回给模型 → 模型继续 → …… → 模型宣布完成。

### 6.2 完整流程

```
用户消息到达（飞书 WS → 网关 → dispatch 到 agent 会话）
  ↓ run 启动：装配上下文（会话历史 + AGENTS.md → system prompt）
  ↓
┌─→ ① LLM 调用（当前上下文发给模型）
│      ↓
│   ② 模型返回：
│      ├─ 纯文本 → loop 结束，交付给用户
│      └─ toolCall → ③ before_tool_call 钩子（门禁检查点）
│           ↓ ④ 网关执行工具 → toolResult 追加进上下文
└────── 回到 ①
  ↓ run 结束：写入 transcript_events，状态更新
```

一次用户消息 = 一个 run = 一段 agent loop：纯问答一轮结束，复杂任务可达上百轮（如 wyj 修复 XMT 时的 200 次工具调用）。

### 6.3 门禁在 loop 中的位置

broadcast-gate 挂在 ③——每个循环里"模型请求调工具"与"网关实际执行"之间。这就是为什么它能强制"先播报再干活"：每个循环轮次都过一次检查。

### 6.4 与统计的对应

dashboard 的"工具调用数"= loop 轮数；"会话数"= run 数量；播报调用数 = loop 中 lark-cli 播报的执行次数。

## 七、WebSocket 相比 HTTP 的缺点与技术谱系

### 7.1 缺点清单（诚实全面）

1. **有状态连接是服务器负担**：每条连接维持内存/文件描述符——百万在线即百万份状态；HTTP 无状态请求完即释放，天然水平扩展
2. **中间设备兼容性**：老代理/负载均衡/企业防火墙可能不认识 Upgrade 头，会阻断或断连——HTTP 人人都懂
3. **失去 HTTP 生态**：无现成缓存、重试语义、标准错误码、成熟监控链路；断线重连、消息确认、背压控制全需应用层自建
4. **横向扩展复杂**：HTTP 可随意轮询；WS 连接固定节点，多实例集群需 sticky session 或跨节点消息总线
5. **消息可靠性弱**：断线重连瞬间可能丢消息，WS 协议不补发（飞书用事件补推 + OpenClaw 用去重机制弥补）
6. **排障更难**：HTTP 可 curl 重放；WS 需抓包分析二进制帧，问题复现依赖连接状态

### 7.2 技术谱系对比

- **短轮询**：客户端定时问"有新消息吗"——实时性差、大量无效请求
- **长轮询**：请求挂住直到有数据才返回——接近实时但每次重建连接、服务器挂请求
- **SSE**：HTTP 单向服务器推送流——简单、走 HTTP 生态，但只能服务器→客户端单向
- **WebSocket**：协议升级、全双工常连接——最实时、最双向，但最复杂、状态最重

### 7.3 飞书/OpenClaw 的选择逻辑

机器人消息必须实时（轮询延迟不可接受）、部署环境多样（大量用户服务器在 NAT 后无公网入站——本机即如此）、双向都需要（收消息 + 发回复）——WS 是唯一同时满足的选择，代价是 OpenClaw 自行承担心跳、重连、去重等可靠性工程（网关日志中的 dedup warmup、ws client ready/closed 都由此而来）。

## 八、几个概念的关系总图

```
            WebSocket 长连接（出站，耳朵和嘴）
   飞书 ◄═══════════════╗
                        ║ ▼ 事件推送
            openclaw-gateway 进程（宿主）
              ├─ feishu 渠道插件 → dispatch
              ├─ agent loop（大脑流程，每 run 一段）
              │    ① LLM 调用 ←→ ② toolCall
              │    ③ before_tool_call【broadcast-gate 门禁】
              │    ④ 工具执行 → toolResult 回流
              ├─ cron 调度器（闹钟）
              └─ 插件宿主
                        ▼ 持久化
              transcript_events / session_nodes / cron_jobs
                        ▼ 读取
              dashboard（统计展示，直读不经网关）
```

- **WebSocket 长连接**：管"听和说"（消息进出）
- **agent loop**：管"想和做"（理解、决策、执行）
- **网关进程**：两者的容器，也是权限的边界（进程 uid = 一切执行的身份）

# 第四篇：多实例知识沉淀——晨间知识蒸馏（9/28）

记录 2026-09-28 落地的"晨间知识蒸馏"机制：如何把 8 个实例、30+ 子 agent 每天的任务流水、报错与解法，自动蒸馏成结构化知识沉淀到各实例 main agent，让 main 越来越懂业务、记得住踩过的坑，且上下文成本恒定。

## 一、背景：知识流水已有，缺的是哪一环

**原始流水层已经存在**（依赖第一篇的成果）：review-furnace 每天凌晨从各实例 `transcript_events` 自动生成子 agent 日报，落盘 `/data/knowledge/agent-daily-report/\<实例>/\<agent>/\<日期>.md`，固定三段——主要任务 / 问题与修复 / 待跟进；root crontab 3:30-5:15 按实例错峰触发（TeamS 3:30、QD 4:45、sxs 5:00、XMT 5:15…）。

**但三个缺口让"坑"沉淀不下来**：

1. **子 agent 数据没有汇入 main 的通道**。日报按 agent 平铺，main 不会自动去读；OpenClaw 内置的 Memory Dreaming Promotion（每天 03:00，按相关度≥0.75、召回≥3 次等门槛把短期记忆晋升进本 agent 的 MEMORY.md）只管单 agent 自身，跨 agent 不感知。
2. **报错解法是流水不是知识**。"问题与修复"混在当日事务里，没有提炼成"坑→根因→解法→适用条件"的可复用形态，换个场景同样的坑再踩一遍。
3. **没有防膨胀的存储设计**。main 的 MEMORY.md 每轮对话注入上下文，直接堆知识会稀释记忆、撑爆预算。

目标一句话：**每个实例的 main 每天自动从子 agent 日报蒸馏知识；存得下、找得到、上下文成本恒定**。

## 二、数据链路：三层结构 + 一条静默升格通道

```
第1层 原始流水  /data/knowledge/agent-daily-report/<实例>/<agent>/<日期>.md
               （furnace 自动生成，全部历史留存，只增不删）
                    ↓ 每日 06:30 蒸馏（只留可复用的因果知识）
第2层 知识正文  <main workspace>/knowledge/lessons-YYYY-MM.md（按月滚动，每条 300~500 字完整因果）
                    ↓ 一条对应一行
第3层 索引      <main workspace>/knowledge/INDEX.md（每条一行：编号|标题|标签|次数|最近日期）
                    ↓ 次数≥3 且非"待考"
升格           MEMORY.md 末尾"业务知识（自动蒸馏）"section 追加单行指针
```

三个文件的分工是**上下文经济学**：

- INDEX（约 2KB）常驻用于"扫目录"——蒸馏查重时读它判断新坑是否与旧条目重复，日常对话遇相似问题时按编号定位；即使积累上千条知识，这份索引也只有几十 KB
- lessons 正文按需打开——拿到根因假设与解法细节
- 日报流水只在需要审计原始证据时回看

## 三、实现：一个 skill + 每实例一个定时任务

**技能**：`morning-knowledge-distill`，六步流程 + 质量红线：

1. 确定参数（实例名/目标日期=昨天/日报目录）→ glob 无日报则静默结束
2. 通读全部日报（禁抽样），提取候选：收"报错→根因→解法→适用条件"与关键业务事实，弃一次性事务与例行巡检；日报写"素材未载明/疑似"的一律标 `待考`，不编造
3. 查重合并：先读 INDEX——同一坑（根因+解法实质相同）在旧条目追加证据不新增；新坑编号 `K-YYYYMM-NN`
4. 写入 lessons 并同步更新 INDEX（完成标准：两文件条目数一致）
5. 静默升格（全自动无人工确认）：次数≥3 且非待考 → MEMORY.md 单行指针；护栏=单次≤2 条、section 超 30 行熔断、`promotion-log.md` 全程留痕
6. 一行统计汇报（输入 N 份，新增/合并/待考/弃各几条）

质量红线：指纹幂等（日期+agent+标题，同日重跑不重复）；单日新增>10 条只留最完整的 10 条；只增不删；二手总结与直接证据冲突时以后者为准。

**调度**：每实例 main 一个 cron（`30 6 * * *` Asia/Shanghai，isolated，delivery=none，在 furnace 最后一批 5:15 之后）：

```bash
T=$(python3 -c "import json;print(json.load(open('/data/agent/openclaw_<X>/.openclaw/openclaw.json'))['gateway']['auth']['token'])")
/usr/local/bin/openclaw cron add --port <端口> --token "$T" \
  --name morning-knowledge-distill --cron "30 6 * * *" --tz "Asia/Shanghai" \
  --session isolated --no-deliver \
  --message "…（自包含：skill 绝对路径 + 实例名 + 日报目录）…"
```

**分实例执行的两个实测坑**：

1. agent 会话里裸跑 `openclaw` 会解析到实例私有 shim（实测解析到 sxs 的 `tmp/agent-cli/openclaw`），任务静默落错实例 → 必须用绝对路径 `/usr/local/bin/openclaw`
2. 改 `HOME`/`OPENCLAW_CONFIG_PATH` 只能"找到"目标网关，仍报 `gateway token mismatch` → 必须 `--port + --token` 显式传目标实例端口（`ops/instance-ports.conf`）与 token（该实例 `openclaw.json` 的 `gateway.auth.token`）

## 四、真实产出（TeamS 首跑实测）

2026-09-28 强制试跑，从 09-27 日报蒸馏出 **10 条知识**（来源覆盖 main/rival/data_group），抽样两条：

# 第五篇：自行分配子agent派发任务——两套派活机制与 data_group 飞书身份修复（10-04/10-08）

记录 2026-10-04 修复 TeamS 实例 data_group 飞书身份（lark-cli）的完整链路，以及 10-08 对其过程播报去向的核查与纠正。核心议题：主 agent 什么时候把任务派给子 agent / 兄弟 agent、什么时候自己动手，以及 lark-cli 在 OpenClaw 上下文里的绑定机制与双配置路径。

## 一、两套派活机制与选用判断

### 1.1 同实例子 agent（分身）

- 用 `sessions_spawn` 产生干净上下文的子 agent，并行干活、结果回传主会话综合；
- 适用：可并行的批量探查（如多实例配置巡检）、大块独立工作（长构建/批量文件改造，隔离上下文防止主会话历史膨胀）、需要沉淀回看的成果（可见会话在侧边栏可随时查看进度与产物）；
- 大规模并行（5 个以上同类任务）另有收集器（collector）模式：统一等全部完成再收集汇总。

### 1.2 跨 agent 派单（openclaw agent --agent）

- 派单形态（实测可用）：

```
env -i PATH=/usr/local/bin:/usr/bin:/bin HOME=/data/agent/openclaw_TeamS \
  /usr/local/bin/openclaw agent --agent data_group \
  --channel feishu --reply-account baiban \
  --reply-to oc_10be8ba31b11d814cfb52964f7879074 --deliver \
  -m "任务简报（背景+步骤+交付物+回报格式）"
```

- 适用场景：目标域知识在对方那里——它自己的凭据路径、实例 cron 注册表、业务脚本。派给它干比隔空操作又快又对；
- `--deliver` 让被派 agent 的最终回复经指定机器人直接投递到指定群（"喊它通知用户"的落地形态）。

**两个实测铁律**：

1. 必须用 `env -i` 全净环境。本会话 shell 里的 OPENCLAW\_\* 残留变量（OPENCLAW_CONFIG_PATH/AGENT_DIR 等）会劫持 CLI 的实例解析——报 `Unknown agent id "data_group"`，HOME 指对了也没用；`env -u` 摘掉几个变量都不够，只有全净环境（仅 PATH + HOME=目标实例根目录）才可靠。
2. 验证看对方的 transcript 铁证（transcript_events 表），不要依赖派单进程的 stdout——后者可能被截断甚至为空，而 transcript 里工具调用参数、toolResult、最终回复齐全。

### 1.3 什么任务不派

- 一眼能干完的（单文件查改、一次接口验证）——派单的开销比干活本身大；
- 强依赖主会话上下文的任务——例如 10-08 上午的额度口径反推：7 个实例的口径、历次修正（9/30 的 19.3 亿、10-06 重置覆盖、周二重置日）全在主会话记忆里，派出去要写千字简报还容易失真。

### 2.1 背景与故障链

| 部分 | 谁做 | 原因 |
|-|-|-|
| 摸清派单姿势、两轮授权尝试 | data_group（派单） | 授权动作发生在它自己的上下文里才有意义（护栏触发、绑定落位都在它的 home）；隔空跑只会得到失真结果 |

一句话总结：**派单解决"只有它能做的事"（自上下文的授权动作），直做解决"不该让它做的事"（凭据手术）**——而不是简单按"谁有能力谁做"分工。

## 六、分工的原理与底层思考机制（深入展开）

这一章把第二章"为什么这样分工"背后的决策原理与思考机制展开说清：派发不是"忙不过来才找人"，而是一套围绕上下文经济学、信息定域、错误成本与验证闭环的工程决策。

### 6.1 第一性原理：上下文窗口是最稀缺的资源

- agent 的一切工作记忆都在上下文窗口里：系统规则、对话历史、工具结果、中间结论——全部占预算，且随任务推进只增不减；
- 主会话上下文有特殊性：它承载与用户的完整历史（口径修正链、项目知识、偏好）。一旦被大批中间结果污染，轻则稀释注意力，重则"失忆"——10-08 上午的额度口径反推若派出去，7 个实例的口径与历次修正（9/30 的 19.3 亿、周二重置日、10-06 覆盖清理）都得写进简报，还可能失真；
- 子 agent 的第一价值是**上下文经济学**：它拥有干净的工作区，脏活的重试、报错、探路都发生在它自己的窗口里，主会话只收最终摘要。用完即弃，主线上下文成本恒定。

### 6.2 决策的四个底层判据

每次"派还是不派"的判断，实际在过四道闸门：

**判据一：信息定域——解决任务的关键知识在哪里？**

| 关键知识的落点 | 决策 | 实例 |
|-|-|-|
| 我的上下文（用户口径、历史修正链） | 不派 | 额度口径反推（10-08 上午） |
| 对方的环境与本地知识（它的凭据路径、实例 cron 注册表） | 派 | data_group 自查晨报双发（10-08 早） |
| 只在执行者自己的上下文才可见（安全护栏、绑定落位、运行时行为） | 必须派 | init 被 lark-cli 护栏拒绝（10-04）——该拦截只在 agent 自己的上下文触发，隔空跑永远看不到 |

第三行最容易被忽略：有些事实是"执行时才在执行者环境里浮现"的，派单是获取这类情报的唯一手段。

**判据二：错误成本——失败有多贵？**

- 试错型任务（跑命令看报错、验证调用姿势、探路）失败成本约等于零，且失败即情报——优先派；
- 手术型任务（写凭据、改配置路径、删数据）失败不可逆或难以回滚——直接做，且必须带备份（镜像前先 cp .bak）。

10-04 的分界线正在这里：两轮授权尝试是试错型（派），提取 appSecret 做双路径镜像是手术型（直做）。

**判据三：并行度——任务能不能拆成互不依赖的份？**

- 批量同质（7 个实例各查一遍、N 个文件同款改造）→ 子 agent 群并行，墙钟时间约等于最慢一个；
- 强时序/强状态依赖（改一处验一处）→ 主线串行，派发反而增加协调成本。

**判据四：验证闭环——谁来证明"做完了且做对了"？**

- 谁运行，谁验证：端到端只有执行者的运行时能证明（18:00:57 那条落群消息用的是 AGENTS.md 同款运行时形态）；
- 但证据看 transcript（transcript_events 表），不看派单进程的 stdout——后者会被截断甚至为空，前者含完整的工具调用参数、toolResult 与最终回复。

### 6.3 派单简报的构造原理：它看不到你的世界

子 agent / 兄弟 agent 启动时是干净上下文，**简报是它唯一的世界观**。简报缺一块，它就瞎猜一块。四要素构造法：

1. **背景**：为什么做这件事（不含背景它会自己重推导一遍，甚至推出相反结论）；
2. **步骤**：可执行的动作序列——含"重读配置文件"这类对抗记忆漂移的显式动作。10-08 纠偏的关键修正正在于此：光告知新 chat_id 不够，它上下文里的旧值会继续生效，必须让它重读 AGENTS.md；
3. **交付物**：明确要什么（结论 / 验证 URL / 文件路径）；
4. **回报格式**：规定最终回复的形态，且回报链路要设计好（--deliver 指定投递目标，或要求"最终回复 = 验证 URL + 一句话操作指引"）。

### 6.4 信任边界：环境即身份，凭据不过简报

- **环境变量是 CLI 解析实例身份的依据**：残留的 OPENCLAW\_\* 变量会让命令落到错误实例（实测 Unknown agent id）。env -i 全净（只留 PATH + 目标 HOME）本质是把执行环境还原为"只包含目标实例的事实"；
- **凭据不进派单简报**：简报全文会被写进对方的 transcript（持久化存储），密钥只能由主 agent 在直接操作中读取（如从 openclaw.json 提取 appSecret 走 stdin 管道）。这也是 2.5 节"手术转直做"的第一理由。

### 6.5 主线不变式：派发外包的是手脚，不是判断

无论派多少活，三件事永远留在主线（主 agent）：

1. **播报**——用户可见的进展（结果叙述、里程碑）必须主线亲自发；子 agent 的过程对用户不可见；
2. **决策**——口径取舍、方案选择、何时转向；派单简报本身就是决策的产物；
3. **综合**——多路结果的结论化：把子 agent 的报告当证据合成判断，而不是把它们的输出当指令转发。

同时维持**承诺-回执闭环**：派出去的每个活都要有明确的完成模式与回报路径；"运行中"不是完成，没有验证路径的派发不应承诺。

### 6.6 决策流程（速查）

```
接到任务
 ├─ 一两个工具调用能干完？ ── 是 → 直接干（派单开销大于任务本身）
 ├─ 关键知识只在对方上下文/环境？ ── 是 → 派单（简报四要素）
 ├─ 可拆成互不依赖的批量份？ ── 是 → 子 agent 群并行
 ├─ 手术型操作（凭据/不可逆）？ ── 是 → 直接做（带备份）
 └─ 派出后：指定回报格式与投递目标 → 等回执 → transcript 取证 → 主线综合结论
```

### 6.7 案例复盘：机制与动作的对应

| 环节 | 机制 | 落地动作 |
|-|-|-|
| 两轮授权尝试 | 信息定域（护栏只在执行者上下文浮现）+ 试错成本低 | 派 data_group 执行 init/bind |
| 停止派单转直做 | 错误成本（凭据手术不可逆）+ 信任边界（凭据不过简报） | 主线提取 appSecret、init --force-init、镜像双路径 |
| 18:00:57 终验 | 验证闭环（谁运行谁验证） | 用 AGENTS.md 同款运行时形态发测试消息落群 |
| 10-08 播报纠偏 | 简报构造（显式"重读配置"对抗记忆漂移） | 纠正指令含重读 AGENTS.md 步骤，transcript 取证确认 |

一句话总结：**派发决策 = 四个判据（信息定域 / 错误成本 / 并行度 / 验证闭环）的逐闸评估；执行质量 = 简报四要素 + 信任边界；主线责任 = 播报、决策、综合永不下放。**

## 七、派发的底层原理：会话模型与上下文传递（10-08 深入）

本节回答两个根本问题：派任务给子 agent 时，"任务背景/要做什么/交付物"是怎么传进去的？子 agent 是不是就是新开一个会话？答案先给出：**子 agent 本质上就是一个新会话，但上下文如何装配、结果如何回收有一套明确的机制**。

### 7.1 三个概念：agent、session、run

- **agent**：一个身份（wyj、data_group），对应 workspace（AGENTS.md/记忆/skills）+ 配置（模型、工具权限）。它不执行任何东西，只是"人格与资产的容器"；
- **session**：一段模型上下文，用 sessionKey 标识（如 `agent:wyj:subagent:a1b2c3`），物理载体是 agent 私有库的 `transcript_events` 表（每条消息一行）；
- **run**：会话里的一次任务执行 = 一段 agent loop（模型思考→工具调用→结果回流→再思考，直到结束）。

**子 agent = 同一个（或指定的）agent 身份 + 一个全新 session + 一次 run**。它不是新进程——agent loop 跑在同一个网关进程里，与父会话的循环完全同构，只是 transcript 相互独立。

### 7.2 背景/任务/交付物的传递：唯一通道是"文本 + 文件"

关键设计：**新会话的 transcript 是空白的，它对父会话的对话历史一无所知**。信息不在它的上下文里，对它就等于不存在。传递机制分两层：

**第一层：spawn 时的 task 文本 → 首条 user 消息。** sessions_spawn 传入的 task 被写进新会话 transcript 的第一条 user 消息（实际落库带 `[Subagent Task]` 标记）。run 启动时做上下文装配，子 agent 看到的第一眼 = OpenClaw 基础系统提示 + bootstrap 文件（AGENTS.md/SOUL.md/USER.md，每个 run 重新注入）+ skills 清单 + **你的 task 文本（首条 user 消息）**。这就是简报必须自包含的机制根源——"用户口径修正链""之前三种形态实测失败"这些只在父会话上下文里存在的事实，必须显式写进 task 文本才能到达子 agent。

**第二层：大块背景走文件系统。** 子 agent 继承父 agent 的 workspace（共享同一文件系统），复杂背景的正规做法是把详细材料写成文件、简报里只给路径让它自己读。这同时是上下文经济学：首条消息保持轻量，重材料按需加载。

### 7.3 完整链路：从 spawn 到结果回传

```
父会话调 sessions_spawn(task="简报", context="isolated")
   ↓
网关在 session_nodes 注册新会话（sessionKey=agent:父:subagent:<uuid>）
   ↓
task 文本写入新会话 transcript_events（第一条 user 消息）
   ↓
run 启动：装配上下文（bootstrap + 任务消息）→ agent loop 独立执行
   ↓（几十上百轮工具调用，全部写进它自己的 transcript）
子 agent 输出最终 assistant 文本
   ↓
结果回传（三种模式，按 spawn 参数定）：
  ① announcing 子：完成事件自动回流父会话（父方 sessions_yield 等待）
  ② collect 群发：父方 agents_wait 显式收结构化结果
  ③ 隐藏子：父方主动读子会话 transcript（sessions_history）取最终回复
   ↓
清理：隐藏子按 cleanup 参数删除或保留；可见子留在侧边栏可回看
```

### 7.4 两种上下文继承模式（"新会话"的两种形态）

- **isolated（默认）**：真·空白会话，只有 bootstrap + 任务文本。适合明确拆出去的独立任务（防止父会话历史污染子 agent 的判断）；
- **fork**：把父会话的转录**复制**进新会话——子 agent 带着父方全部对话记忆开跑（要求同一 agent）。适合"以当前心智继续干一件分支活"。

所以准确表述是：子 agent = 新会话 + **可选的上下文继承策略**，"是不是全新"由参数控制。

## 八、subagents.allowAgents：实例内白名单与跨实例边界

### 8.1 参数定义与语义

schema 位置（zod 校验确认存在，但**不配置即走默认**，本服务器所有实例的 openclaw.json 均未显式配置）：

```
agents.entries.<id>.subagents.allowAgents: string[]   ← 每 agent 覆盖
agents.defaults.subagents.allowAgents: string[]       ← 实例级默认
```

语义：**sessions_spawn 显式指定 agentId 时的目标白名单**。默认值 = 仅同一 agent。实测验证：在 sxs 以默认策略尝试 spawn 同实例的兄弟 agent jwh，直接被拒——`forbidden: agentId is not allowed for sessions_spawn (allowed: wyj)`。文档另有两个细节：显式设置白名单后要把自己也加进去（否则自指派单也被拒）；agent 配置已删除的 stale 条目会被 sessions_spawn 拒绝并从 agents_list 剔除，跑 `openclaw doctor --fix` 清理。

### 8.2 能否跨实例填？——不能，agent id 是实例内注册表键

在 TeamS 的 allowAgents 里填 "wyj"（意图引用 sxs 的 wyj）**行不通**，机制原因：

1. allowAgents 里的 id 对着**本网关的 agent 注册表**解析——sessions_spawn 走本实例网关，目标必须在同一个网关的 agents.entries 里配置过；
2. sxs 的 wyj 在 TeamS 网关注册表里不存在，填进去的结果是一条永远无法解析的死条目，而不是"引用 sxs 的 wyj"；
3. 文档的 stale 条目处理逻辑佐证了"每个条目必须能在本地注册表找到配置"的设计。

**变通方案的坑（不推荐）**：在 TeamS 的 agents.entries 里新建一个叫 wyj 的 agent、workspace 指到 sxs 目录——那是在 TeamS 网关里造了一个"镜像 wyj"（共享文件但双网关运行、凭据路径指向 sxs、会话状态分裂），违反第零铁律的身份隔离。

### 8.3 正确的跨实例姿势：不在 spawn 层，在网关 API 层

跨实例派单不经过 allowAgents，而是**对目标实例网关的直接 API 调用**（即第二章 data_group 派单的形态）：

```
env -i PATH=... HOME=/data/agent/openclaw_TeamS \
  openclaw agent --agent data_group --port 18793 --token <TeamS网关token> -m "简报"
```

`--agent data_group` 由 TeamS 网关解析（它自己的注册表认识 data_group），`--port + --token` 完成跨实例寻址与鉴权。两层机制对照：

| 层 | 管什么 | 白名单/鉴权 |
|-|-|-|
| sessions_spawn + subagents.allowAgents | **实例内**派子 agent | 本网关注册表 + allowAgents |
| openclaw agent --port + --token | **跨实例**派单 | 目标网关 token 鉴权（目标实例自己的 agent 注册） |

一句话总结：**allowAgents 是"实例内 spawn 目标的防火墙"；跨实例协作走网关 API + token 鉴权，两者是不同层的机制，不要试图用 allowAgents 实现跨实例引用。**

# 第六篇：Agent Harness 底层原理——模型之外的一切（10-09，10-19 增补官方文档系统梳理）

本篇记录 2026-10-09 关于 harness 与钩子层的讨论，并补遗 10-08 晚间同属"运行机制"主题、当时未入档的三段讨论（skill 选择机制、语义相似度与 Transformer、sandbox 与实例隔离）。10-19 增补：依据官方文档（agent-runtime-architecture、concepts/agent-loop、context-engine、agent-runtimes、queue、memory-architecture、session-state）系统梳理 harness 底层原理，与本章前文的直觉视角互补——见篇末"增补"各节（概念分层、官方 run 序列、上下文引擎、队列与并发、模型运行时代际、状态与记忆、心智图与自愈）。全篇注重原理与机制，案例均为本服务器真实运行记录。

## 一、Harness 是什么：模型之外的整套装甲

**起点是 LLM 的能力边界**：它只会"根据上文生成下一个 token"——不能执行命令、不能记忆、不能等待、不能主动发消息。把"生成文本"变成"能干活的 agent"，靠的是外面那层脚手架，即 harness：

| 部件 | 职责 | OpenClaw 对应物 |
|-|-|-|
| 接入层 | 消息怎么进来 | 渠道插件（飞书 WS 长连接等） |
| 记忆 | 上下文装配与持久化 | transcript_events + bootstrap 文件 + MEMORY |
| 工具执行器 | 把"我想调 exec"变成真的执行 | 网关工具注册表 + 执行器 |
| 钩子/门禁 | 哪些调用放行、拦截、改写 | 插件钩子（before_tool_call 等） |
| 调度 | 无消息时何时醒来 | cron_jobs / automations / heartbeat |
| 交付 | 最终文本回到用户面前 | 渠道插件出站 |

行业对照：Claude Code / Codex CLI 是"终端型 harness"（SWE-bench 的 harness 则是评测脚手架）；OpenClaw 是**消息原生的多 agent harness**——飞书进出、cron 调度、多会话、插件门禁全是它的一部分。

准确表述：**agent 不是"使用"harness，而是"运行在"harness 里**——全部 agent 能力都由它定义。抽掉网关，剩下的只是一个会聊天但什么也做不了的 GLM。

## 二、执行 Loop 的完整运行（以一条真实消息为实例）

```
用户消息（飞书）
  ↓ ① 接入：飞书 WS 长连接推送 → 网关 feishu 渠道插件
  ↓ ② 分发：路由到会话 agent:wyj:feishu:direct:ou_xxx
  ↓ ③ 会话装配：读 transcript_events 重建历史
  │     + 注入 bootstrap（AGENTS.md/SOUL/USER + available_skills 索引
  │       + 运行时快照：时间、无活跃 exec、无活跃子 agent）
  ↓ ④ agent loop：
  │   ① 全部上下文 → LLM（日志可见 model=... status=200）
  │   ② 模型返回：纯文本 → loop 结束进 ⑥；带 toolCall → ③
  │   ③ 钩子层 before_tool_call（broadcast-gate 挂在这里）
  │      放行 → ④；拦截 → blockReason 作为 toolResult 喂回 → 回 ①
  │   ④ 网关执行工具 → toolResult 追加进上下文
  │   ⑤ 回到 ①（一次任务几十上百轮）
  ↓ ⑥ 交付：最终文本经渠道插件发回飞书
  ↓ ⑦ 全程事件流式写入 transcript_events（下次装配的数据源）
```

三个亲历铁证：

1. **门禁拦截**：10-08 15:54 wyj 查 QD 蒸馏条目数，第一发 exec 被 `PROGRESS_BROADCAST_REQUIRED` 弹回——第③步物理发生的拦截，blockReason 作为工具错误喂回，下一轮补播报后原调用重试成功，全程无人工；
2. **循环体量**：10-04 修 data_group 播报通道的 run 跑了 200+ 次工具调用，每轮都是"请求→门禁→执行→回流"一圈；
3. **上下文装配即记忆**：跨天的对话"记得"前几天聊过什么，不是模型有记忆，是第③步每次从 transcript 重建历史喂进来——这就是"心智连续性 = harness 用文件重建"的含义。

## 三、Loop 的四种增强形态

1. **后台执行不阻塞**：exec 可背景化（yieldMs）——如 10-08 的 npm run build（会话 good-mist），loop 立即拿到"still running (pid)"继续别的步骤，之后用 process 工具拉日志；
2. **派生循环**：sessions_spawn 开出子会话后，子 agent 有自己独立的一套 loop（同构、独立 transcript）；父方 sessions_yield 结束本轮 turn——loop 暂停而非结束，子会话完成事件把父方唤醒，新 loop 从"收到完成通知"继续；
3. **无消息唤醒**：cron/automations 是"到点强制开一个 loop"——每日 06:30 各实例蒸馏 job 就是网关调度器启动的 isolated 会话 loop，跑完即终；
4. **流式卡片**：飞书端 block 模式下，loop 中途输出的文字实时刷进卡片——这是"边干边说"播报规则能被用户看见的传输基础。

## 四、钩子层：定义、位置与能力

**定义**：钩子（hook）= harness 在自己的执行流程里预留的标准化挂载点，外部代码（插件）向挂载点注册函数，流程走到时被回调——可以观察、拦截或改写正在发生的事。同构案例：浏览器事件监听、Git pre-commit、nginx filter、Express 中间件。**主流程不可变，行为可扩展**。

**在 harness 中的精确位置**：第③步——模型的"请求"与网关的"执行"之间的缝隙。模型只能表达"想调什么工具"，真正执行者是网关；这条缝隙是唯一的物理卡点，错过它工具就真跑出去了，只剩事后审计。

**三类能力**：

| 类型 | 做什么 | 实例 |
|-|-|-|
| 拦截 | block 调用、要求人工审批 | broadcast-gate 弹回未播报的调用 |
| 观察 | 只记录：审计、统计、告警 | broadcast-gate 的 log 模式（试跑期） |
| 增强 | 改写参数、注入上下文 | OpenClaw 主要用于对话类钩子 |

## 五、钩子实战：broadcast-gate 的自愈闭环

状态机规则（按 runId 维护）：

```
模型调工具 → 钩子检查本 run 是否发过播报
  ├─ 未播报且任务刚开始 → {block:true, reason:"PROGRESS_BROADCAST_REQUIRED..."}
  ├─ 已播报但静默超 5 分钟 → {block:true, reason:"MILESTONE_STALE..."}
  └─ 合规 → 放行
```

被拦截后的自愈闭环（零人工）：blockReason 文本作为"工具执行错误"注入模型上下文 → 模型下一轮读到补救指引（含播报命令模板）→ 执行播报 → 钩子识别为播报调用并更新状态机 → 重试原工具 → 放行。9 月底铺规则以来 17 条弹回记录全部自愈，未卡死任何任务。

## 六、Harness 决定能力边界的三个推论

1. **能做什么 = 工具注册表里有什么**：模型再聪明，harness 没注册的工具连"想做"都表达不出来；工具策略过滤就是在这一层裁剪；
2. **受什么约束 = 钩子层写什么**：AGENTS.md 是软约束（只是上下文里的 token，靠注意力被"看见"，长对话中自然衰减）；before_tool_call 钩子是硬约束（代码级判断，轮轮必过）。两轮核查实证：纪律层播报执行率约 50% 且"优等生退步"，钩子层铺开后弹回即合规零漏网；
3. **心智连续性 = transcript + memory + bootstrap 文件**：loop 每次醒来都无状态，连续性完全是 harness 用文件系统重建的——"Text > Brain 📝"规则的技术根源：只有写进 harness 管理的文件，才会在下次装配时回到眼前。

## 七、补遗（10-08 晚）：skill 选择机制——两段式懒加载

- **机制**：runtime 不做关键词匹配。每个 run 注入的只有全部 skill 的 name + description（索引层）；模型用语言理解做语义匹配，命中后才 read 对应 SKILL.md 正文（数据层）。几十个 skill 只占几千 token 常驻——与子 agent 简报同一上下文经济学；
- **多相似 skill 的判据**（按优先级）：任务粒度（端到端工作流 > 原子操作）→ 目标载体（wiki/docx/表格/群消息，description 各自声明）→ 动词（读/写/导航/排障）→ 具体压倒一般（most specific wins，系统纪律）；
- **description 工程**：开头即触发短语（把用户会说的词写进去）、一个分支一个触发点、相近 skill 互相路由（"表格数据走 lark-sheet-data-ops"——skill 间自发组成分诊网，正文路由是模型能执行的指令，向量相似度给不了）；
- **兜底**：真二义先问；选最可能的读入、发现不对就换（读成本低）；同名冲突按加载优先级仲裁（per-agent > 实例共享 > plugin-skills）。

## 八、补遗：语义相似度是注意力的涌现，不是向量计算

- **事实**：skill 选择路径上没有 embedding、没有向量库、没有余弦相似度、没有独立检索步骤——全部候选与用户输入同场（同一次前向推理），选择本身就是生成的 token；
- **与 RAG 对照**：向量检索输出显式分数/排序/阈值，是"先检索后生成"两阶段；in-context 匹配无分数无阈值，选择与生成同一次推理，失败模式是 description 含糊导致选偏；
- **OpenClaw 双范式并存**：memory_search（记忆召回）真用向量语义索引（候选集大、需要排名、有 minScore）；skill 选择用 in-context（候选集小、全常驻）。工程判据 = 候选集规模：几十条直接进上下文，成千上万才值得向量预筛；
- **注意力匹配强于余弦的三点**：零词面重叠的意图命中（"白板又报 230002"→ channel-delivery-diagnosis）；能执行 description 里的路由指令；条件分支匹配（触发说法穷举的语境判断）。代价是概率性、不可调参——唯一杠杆是把 description 写得更贴近用户真实说法。

### Transformer 原理速览（"注意力涌现"的物理层）

- 数据流：分词 → embedding+位置注入 → N 层 Block（多头自注意力 → 残差 → MLP → 残差）→ 输出头 softmax → 采样下一 token → 自回归循环；
- 注意力四步：scores = Q·Kᵀ（两两点积算相关度）→ /√d_k 缩放 → softmax 归一化 → weights·V 聚合。因果掩码屏蔽未来位置（生成不偷看 + 训练可并行）；
- 多头 = 多视角并行（语法头/实体头/意图匹配头各司其职）；MLP 占参数大头（世界知识的键值记忆库）；残差+LayerNorm 让百层堆叠可训；
- 推理经济性：KV Cache 缓存历史 K/V（显存随序列线性涨）+ 注意力 O(n²)——上下文为什么是稀缺资源、prompt 为什么越长越贵、"description 索引 + 正文按需加载"为什么值得，全部由这两条决定。

## 九、补遗：sandbox 现状与 per-user 实例隔离

**现状实证（10-08 查证）**：wyj 以 uid=0 root 裸奔（无容器、宿主为 KVM 虚机、config 无 sandbox 键）——刻意取舍：跨 8 实例运维（systemctl/chmod/跨实例写）与沙箱边界根本冲突。但**实例隔离已用 Unix 用户实现大半**：6/8 实例网关以专属 ocs\_\* 用户运行（GTM/GYL/need/PJT/QD/XMT），仅 TeamS 与 sxs 为 root。

对"每个实例用沙箱能否保证只碰自己文件"的三段回答：

1. **写隔离：已是现实**——实例目录属主 ocs\_*:ocs\_*，跨实例写入被内核拒绝（uid 不匹配），不需要 Docker；**读隔离：未收紧**——文件默认 world-readable，ocs_gtm 可读 TeamS 的配置与日报，收紧需实例目录 700 + 共享资源白名单化；
2. **命令能力：会削减，且是故意的**——非 root 实例用户做不了 systemctl/chmod 全局/setpriv，这正是隔离的意义：跨实例运维能力收归 root 管理实例（sxs/TeamS），分层授权而非人人 root。Docker 式沙箱更彻底（容器内物理看不到他实例路径，共享资源只读挂载），代价是镜像内须预装 lark-cli/python3 等工具链，且宿主级命令天然不该进沙箱；
3. **共享读与隔离能共存——已有活体证据**：10-08 的 /data/knowledge 缺执行位 x 事故（四实例蒸馏空跑）正是"非 root 用户读共享目录"失败的样本；修复（chmod -R a+rX，全局读+目录遍历、不给写）后，GTM/QD 以 ocs_gtm/ocs_qd 非 root 身份完整跑通蒸馏。模式定型：**共享资源显式授权清单（全局读、无写）+ 实例私有路径严格属主**。

残余边界（文件权限管不到）：/tmp 全机共享（粘滞位只防互删）、localhost 互达（无 token 进不了网关 API）、系统资源不隔离。加固演进路径：主实例保 root（运维需要），不可信子任务按 spawn 的 sandbox 参数丢容器——收窄爆炸半径而不缩能力。

## 十、本篇小结

- **Harness = 模型之外的一切**（感官/记忆/手脚/门禁/调度），agent 运行在其中而非使用它；
- **Loop = 装配上下文 → 模型生成 → 钩子检查 → 执行工具 → 回流循环 → 交付落库**，连续性与约束都由 harness 层供给；
- **钩子层 = 意图与行动之间的物理卡点**，把约束从提示词劝告升级为执行级强制（broadcast-gate 的弹回-自愈闭环是活体样本）；
- **skill 选择 = 注意力涌现的语义匹配**（description 是索引），与向量检索是两种范式，按候选集规模选用；
- **隔离 = per-user 已实现写隔离，共享读靠显式授权**，命令能力削减是隔离的定价。

### 增补一、官方概念分层与 harness 家族

四层概念（排障先分清问题在哪层）：

| 层 | 例子 | 职责 |
|-|-|-|
| Provider | `anthropic`、`openai`、`zhipuglm` | 认证方式、模型发现、模型命名 |
| Model | `GLM-5.3-flash` | 本次 turn 用哪个模型 |
| Agent Runtime | `openclaw`、`codex`、`copilot`、`claude-cli` | 执行这个 prepared turn 的底层循环/后端 |
| Channel | 飞书、Discord | 消息进出 |

Harness 与 Runtime 的关系：runtime 是配置/概念层，harness 是提供这个 runtime 的**实现**（代码态称呼）——内置 Codex harness 实现了 `codex` runtime；注册表与选型策略在 `src/agents/harness/`。

两个家族：**内嵌 harness** 跑在 OpenClaw 自己的 agent loop 里——`openclaw`（内置默认，核心在 `packages/agent-core`，入口 `src/agents/embedded-agent-runner/`；旧别名 `pi` 归一为 `openclaw`）、`codex`（仅精确官方 Responses 端点且无请求改写时隐式选中，`openai/*` 前缀本身不触发）、`copilot`（Copilot CLI 独立 opt-in 插件）。**CLI 后端**起本地 CLI 子进程但保持模型 ref 规范（如 `claude-cli`）——它不是 embedded harness id，不能传给 AgentHarness 选型器。

选型策略：model/provider 级 `agentRuntime.id`（model 条目优先）；`auto`（默认）= 先找支持当前 provider 路由的插件 harness，否则回落内置 `openclaw`；provider/model 前缀本身永不选中 harness。

### 增补二、官方 run 序列（RPC 视角，与前文飞书视角互补）

```
agent RPC（校验参数 → 解析 sessionKey → 持久化元数据 → 立即返回 {runId, acceptedAt}）
→ agentCommand（解析模型/thinking 默认 → 载入 skills 快照 → 调 runEmbeddedAgent）
→ runEmbeddedAgent：
   ① per-session 队列 + 全局队列串行化（见增补四）
   ② 解析模型 + auth profile
   ③ 会话与工作区准备：workspace 创建 → skills 注入 → bootstrap 注入 system prompt
      → transcript 目标 + 写者声明流式前就位
   ④ 系统提示组装：基础 prompt + skills + bootstrap + per-run 覆盖；强制上下文上限与 compaction 预留
   ⑤ 模型流式推理 → 工具执行 → 回流 → 循环直到停止
→ 三条事件流：lifecycle / assistant / tool
→ agent.wait 返回 {status, terminalReply, terminalReceipt}；
   sourceReplyDelivered=true 才算最终回复真到达外部会话（不拿显示历史当投递证据）
```

### 增补三、上下文引擎、写入栅栏与回复整形

**上下文引擎**是可插拔组件（`plugins.slots.contextEngine`，默认 `legacy`），在四个生命周期点参与：**Ingest**（新消息入会话可自存储/索引）、**Assemble**（run 前返回预算内的有序消息集 + 可选 systemPromptAddition）、**Compact**（窗口满或 /compact 时摘要旧历史）、**轮次结束后**（持久化、后台压缩、跨 subagent 边界管理）。legacy 引擎不额外存储、压缩委托内置摘要；插件引擎可换成 RAG 式检索注入；`before/after_compaction` 钩子只观察不可否决。

**transcript 写入栅栏（writer fence）**：被准入的 run 流式前记录持久化 `activeWriterRunId`；每次追加/改写携带 `expectedWriterRunId`，SQLite 同步事务校验匹配——被取代的旧 run 写入被拒，杜绝脏写。再叠加 per-agent SQLite 写队列 + 网关 state 目录锁。这是前文"心智连续性由文件重建"的并发安全底座。

**回复整形**：`NO_REPLY` 过滤；消息类工具发送追踪去重；run 以工具失败收尾且用户将无回复时才出现兜底警告；工具批次结算完却没组合出答案时可做一次无工具 finalization pass（不重复已完成工具）；被拒绝执行等致命失败仍算失败。

### 增补四、队列与并发：为什么串行化、四种模式

**为什么串行化**：同会话并发 run 会同时写同一 session、竞争同一 transcript 写者、争抢上游限流——队列保证同 session 同一时刻只有一个活跃 run，跨会话仍安全并行。

**两层结构**：per-session lane（`session:<key>`，并发 1，CLI/内嵌/Codex 共用）+ 全局 lane（main，受 `agents.defaults.maxConcurrent` 约束，上限 `min(16, max(8, CPU 核))`；subagent lane 默认 8）；cron 等独立 lane 不阻塞入站回复。

**四种模式**（新消息到达时如何与活跃 run 交互）：

| 模式 | 行为 | 适用 |
|-|-|-|
| `steer`（**默认**） | 立即注入当前 run：在跑的工具跑完、未启动的顺序调用跳过，在下一工具/决策前生效；不支持时降级等 run 结束 | 中途纠偏 |
| `followup` | 不转向，逐条排队续跑 | 每条都要完整处理 |
| `collect` | 不转向，静默窗口内合并成一条 followup；跨渠道分别排空保路由 | 连发补充信息 |
| `interrupt` | 中止当前 run，改跑最新消息 | "别做了，换任务" |

配套：500ms 防抖、每会话 cap 默认 20、满了 `drop: "summarize"`。可全局/按渠道/按会话（/queue）覆盖。（口径更正：默认是 steer，早前笔记误记 collect。）

### 增补五、模型运行时代际（generations）——配置变更的原子性

**问题**：模型运行依赖 auth 凭据、模型注册表、投影后的模型目录三组状态，可能被并发修改（换 key、插件发布、配置更新）——一次运行读到一半旧一半新，就会"用旧 key 调新路由"。

**方案**：网关启动/配置变更/插件或 auth 发布时，为每个 agent 构建**原子快照**（三组状态合一）即一个"代际"；每次运行从快照 **fork** 可变存储，不碰共享底层；browse/status/cron/doctor 等路径读发布后的目录，不重复文件系统发现。**关键规则：失败或过期的代际绝不与更新的部分代际并存——必须先发布完整替换。**

**运维指导意义**：换 API key 后必须「paste 写库 → 重启网关刷新内存快照」——不重启，持久层是新 key，内存还是旧代际快照，运行看不到。

### 增补六、状态与记忆

**状态落盘**：`state/openclaw.sqlite`（共享：session_state_events、watch cursors、cron_jobs、audit_events）；`agents/<id>/agent/openclaw-agent.sqlite`（per-agent：auth profiles + 运行时状态，session 行也在此库）；`agents/<id>/sessions/`（transcript）；`credentials/`（渠道凭据）。

**会话状态感知**：持久信号日志（`session_state_events`，只记元数据与一行摘要）+ Watchers（游标三来源：spawn 边自动播种 / ambient 群组 / 显式 watch:true）+ 对账（一条合并的过期通知 + `session_status` 的 `changesSince` 精确拉增量）。状态版本=日志最大序号，修剪后仍存活。

**记忆五原则**（记忆 = 普通文件 + SQLite 索引，按信任分层）：① 无隐藏状态——模型只记得 workspace 文件里写的；② **写比读难**——检索层已足够强，瓶颈在写入时策展，策展移出回复路径放进后台 pass（dreaming，即 03:00 的 Memory Dreaming Promotion）；③ **写入路径即安全边界**——投毒事实写入后事后扫描认不出，安全前移：强制来源（provenance）+ 结构性门禁（晋升由确定性代码控制）；④ 确定性门禁内的模型判断——评分/阈值/匹配全是确定性代码；⑤ **记忆故障绝不阻塞回复**——每个记忆步骤有超时或回退，挂了只降级召回、绝不吞 turn。

### 增补七、一页心智图与故障自愈

```
飞书 ◄──WS 出站长连接──► openclaw-gateway（每实例一个进程）
                            │
                    agent RPC → runId 入队（session lane → global lane）
                            │
            runEmbeddedAgent：会话/工作区准备 → 系统提示组装（base+skills+bootstrap）
                            │
                    上下文引擎 Assemble（预算内消息集）
                            │
              ┌─ agent loop：模型流式 → toolCall ──► before_tool_call（门禁/审批）
              │                    ▲                    │
              │              结果回流 ◄── 净化 → transcript（writer fence 栅栏写入）
              └──────── 循环直到模型停止 ────────┘
                            │
        回复整形（NO_REPLY 过滤/去重/兜底警告/finalization）
                            │
        交付（terminalReceipt 确证送达）→ lifecycle end → audit 投影
```

**故障自愈顺序（模型侧）：模型空闲看门狗（云 120s/自托管 300s）→ 有界同模型恢复（保 transcript 续跑）→ auth profile 轮换（带冷却）→ model fallback（只用于当前 turn）→ 15s 宽窗重试 → runtime 预算（默认 48h）到期 abort。harness 自身恢复链完善，宿主机资源层（磁盘/内存）才是盲区**——这正是 agent 集群健康监控的价值位。

# 第七篇：数仓单表 MCP——底层原理、授权链路与实例接入（10-12）

本篇整理自 GTM 实例 main（GLM-5.3-flash）2026-10-12 与田哥的会话记录：代理层与协议部分由该 agent 逐行读本地 mcp-proxy 源码核实；网关内部（SQL 翻译、数仓引擎）以官方使用文档为准，该 agent 看不到网关源码。wyj 对 token 到期时点做了独立复测（第七节）。

## 一、整体架构：四层结构与 proxy 的存在理由

```
┌─────────────────────────────────────────────────────┐
│ ① AI 客户端层（OpenClaw 实例）                        │
│    把 3 个工具注册给模型：                             │
│    Aihuishoubi_mcp__table-search / describe / query  │
└──────────────┬──────────────────────────────────────┘
               ② JSON-RPC over STDIO（stdin/stdout，本机进程）
┌──────────────▼──────────────────────────────────────┐
│ ③ mcp-proxy（本地代理，@aihuishoubi/mcp-proxy v1.0.3）│
│    · 协议转换：STDIO ↔ streamable HTTP               │
│    · 身份管理：CAS 登录 / token 缓存 / 自动续期        │
└──────────────┬──────────────────────────────────────┘
               ③' HTTPS POST + Bearer token（公司内网）
┌──────────────▼──────────────────────────────────────┐
│ ④ 网关 bimcp-gateway.aihuishou.com                    │
│    · 认证鉴权（按工号：服务权限/表权限/敏感字段权限）    │
│    · 结构化查询参数翻译成单表 SQL 提交数仓引擎执行      │
│    · 结果截流：小结果直接回，大结果落 CSV 给下载地址    │
└──────────────┬──────────────────────────────────────┘
               ⑤ 数仓引擎执行查询（Datamap 上线的物理表）
```

**为什么中间要有 mcp-proxy 这一层**：网关要求公司 CAS 交互式登录 + token 定期续期，而 AI 客户端（OpenClaw/Codex/豆包…）只会一种通用语言——MCP。代理把「认证+续期+转发」的脏活封装掉，任何支持 STDIO MCP 的客户端即插即用，客户端侧全程不需要碰任何凭据。

## 二、协议层：MCP 的本质是 JSON-RPC 2.0

本机这一段只有四种消息来回：

| 方法 | proxy 的动作 |
|-|-|
| `initialize` | 本地直接应答（不透传） |
| `notifications/initialized` | 忽略 |
| `tools/list` | 先向网关远程握手，再透传 tools/list，按 MCP_ALLOWED_TOOLS 白名单过滤后返回 |
| `tools/call` | 向网关远程握手，透传 tools/call，原样回传结果 |

所谓「三个工具」本质是网关侧的三个**远程过程**：`table.search`（查数据地图元数据）、`table.describe`（读表结构元数据）、`table.query`（提交单表查询任务）。`Aihuishoubi_mcp__table-search` 这种长名字的前缀是 **OpenClaw 本地注册时**加的（服务器名+工具名，防不同 MCP 服务重名），不是网关定义的。实测 TeamS 与 GTM 的 tools/list 都只返回这三个工具——没有更多隐藏工具。

## 三、身份与安全：token 从哪来、怎么续（源码级）

### 3.1 首次认证 = 标准 OAuth2 授权码模式 + PKCE，回调走本机回环

1. proxy 在 127.0.0.1 随机端口起一次性 HTTP 服务；
2. 生成 43 字符 code_verifier，SHA256 换出 code_challenge，配随机 state（防 CSRF）；
3. 向网关 POST /auth/cas/sessions 换 browserUrl（有效期 ≤600 秒、一次性），调 xdg-open 拉起浏览器；
4. 用户在浏览器完成公司 CAS 登录 → 网关 302 回 http://127.0.0.1:<端口>/callback?code&state；
5. proxy 严格校验（state 精确比对、Host 头必须精确等于 127.0.0.1:port、code 格式白名单），再用 code_verifier 向 POST /auth/cas/token 换 accessToken + refreshToken；
6. 原子落盘：临时文件写 → fsync → rename，权限 0600、目录 0700，防符号链接攻击（O_NOFOLLOW）和目录偷换（写前写后 realpath 复核）。

### 3.2 日常使用 = 三级自愈链

1. **本地验期，零开销**：accessToken 是 JWT，proxy 自己解 payload 看 exp——没过期直接用；
2. **静默续期**：过期了拿 refreshToken 调 POST /auth/refresh 换新 accessToken，原子落盘，对上层透明；收到 401 也会触发同一套续期+重试；
3. **refresh 也失效才需要人工**：重新走 CAS 浏览器登录。

**正常人只登录一次，之后无感**——但见第七节：refresh 是 7 天硬有效期，到期必须人工重登。

### 3.3 token 绑定网关+环境

token 文件里绑定了 gatewayOrigin + environment，换环境/换网关的旧 token 直接作废——这是「实例间 token 不互串」的机制保证之一（叠加各实例独立 MCP_TOKEN_CACHE_DIR，实现身份/权限/审计三层隔离）。

## 四、一次查数的完整数据流

以「统计 9 月每天已支付订单量」为例：

```
你（中文）→ OpenClaw 模型决策（不写 SQL）
  1. table.search("订单支付金额")     → 网关查数据地图【元数据】，返回候选表清单
  2. table.describe("dm.xxx_order")  → 字段名/类型/粒度/必填日期约束【元数据】
  3. table.query({表, 字段, filter:状态=已支付, groupBy:日期, 日期范围})
       → proxy 打包 JSON-RPC → POST /mcp (Bearer token)
       → 网关：验 JWT → 按工号查三层权限（服务✓表✓敏感字段✓）
              → 翻译成单表 SQL → 提交数仓引擎执行
       → 结果回流：预览 ≤100 行直接返回；大结果生成 CSV（≤10 万行，24h 有效）给下载 URL
  4. OpenClaw 拿到结构化结果 → 整理成中文答案（表名+字段口径+筛选+单位+requestId）
```

三个要点：

- **前两步只碰元数据，不碰数据**——这就是为什么权限不够的人能「搜到表、看到字段」，但一查就报无权限（报错里带数据负责人姓名+工号，方便找谁批）；
- **SQL 是网关翻译的**，用户和 AI 都不提交原生 SQL；也因此只支持单表、不支持 JOIN；
- **权限控制在网关侧执行**，proxy 只是带 token 的传话人——配好 MCP ≠ 能查数，审批才是数据的钥匙。

## 五、table.query 如何变成 SQL：两段式翻译，网关不用大模型

关键分工：**自然语言→结构化参数在 agent 侧由大模型完成；结构化参数→SQL 由网关确定性拼装**。四条证据：

1. `table.query` 的接口契约是**强结构化**的：字段必须用真实列名、聚合只许枚举值（NONE/SUM/COUNT/COUNT_DISTINCT/AVG/MIN/MAX）、筛选操作符也是枚举（EQ/IN…，支持 AND/OR 树）、groupBy/orderBy/previewRows 全是结构化字段——没有任何自由文本进查询参数；
2. 唯一的文本字段 userQuestion，接口注释写明「仅用于查询记录」——审计留痕字段，不是生成输入；
3. 指标口径的 SQL 片段是数据工程师在数据地图里**预定义好的**（如 `SUM(CASE WHEN is_dispatch_flag = 1 AND ondoor_arrive_dt IS NOT NULL THEN 1 ELSE 0 END)` 这种完整公式），网关只是按参数拼装模板+挂预定义公式；
4. 查询延迟是查询本身的耗时特征（秒级\~分钟级随数据量），没有 LLM 生成环节的延迟与抖动；使用文档也明确「不接收原始 SQL」。

整条链：**中文需求 →（agent 里的 LLM）选表/选字段/定筛选聚合 → 结构化 JSON →（网关，确定性代码）拼 SQL → 数仓执行**。LLM 只在 agent 侧，碰不到 SQL 生成。

## 六、硬限制（网关侧强制）

单表无 JOIN ｜ 不收原生 SQL ｜ 预览默认 10 行上限 100 行 ｜ CSV 上限 10 万行/24 小时过期 ｜ 单账号并发 10 个查询 ｜ 单次查询最长 30 分钟。

用法推论：大需求要拆日期分片；优先查汇总表而非明细表。

## 七、token 有效期实测与续期排期

实测数据（GTM main 源码级观察 + wyj 独立复测 JWT 解码）：

| 实例 | accessToken | refreshToken 到期 | 工号(sub) | wyj 复测 |
|-|-|-|-|-|
| TeamS | 15 分钟自动续 | **10-18 18:00:00** | 1146（田哥） | ✓ 与报告一致 |
| GTM | 15 分钟自动续 | **10-16 00:23:54** | 186125（陈巧源） | ✓ 与报告一致 |

- **refresh 7 天是硬有效期，且观察到非轮换迹象**：GTM 到期点 = 首登（10-09 00:23）+ 7 天整——中间的静默续期只换 accessToken，不延展 refresh 过期。这意味着**每周人工重登是固定仪式**（到期后续期链断裂，必须重新走一次 CAS 浏览器登录）；
- **待阿祖拍板的排期**：把 GTM 重登、TeamS 重登与 QD 胡彬首登、PJT 唐月月首登合并成一个集中登录窗口（一次隧道、四人各约 3 分钟，建议 10-15 下午）；同时建议找 MCP 平台（徐作楠）确认 refreshToken 能否延长有效期或支持轮换续期，否则每周重登成为常态。

## 八、GTM 状态修正：一次短暂服务权限异常

田哥质疑「巧源不是早就开通了吗」后，GTM main 重新排查并修正了此前的误诊：

| 时间（10-12） | 事实 |
|-|-|
| 前几天 | 巧源一直正常使用（权限早已开通） |
| 白天 → 15:10 | 网关对其账号返回**空工具列表**（15:10 亲测复现：认证通、tools=[]，GTM agent 因此报 -32602/-32603） |
| 15:21–15:41 之间 | **权限恢复** |
| 15:46 复测 | tools/list = 3 个工具 ✅ |
| 15:47 端到端实查 | 真实跑一次 table.search，返回 345 张候选表，与 TeamS 完全一致 ✅ |

**修正后的结论**：不是「从未开通权限」，是网关侧对其账号出现了一次**短暂的服务权限异常**（约 15:10–15:41）。异常原因本地不可见（权限审批台账在平台侧），需 MCP 平台管理员查审批单状态轨迹（审批到期复查/权限回收重挂/平台变更等）。

**衍生风险提示**：这类「权限瞬时失效」以后还可能发生，症状就是 -32602/-32603 + 空工具列表——处置是等一等或找平台管理员，不是本侧配置问题。（另注：同日 15:05/15:46 的令牌属主 root 事故是独立问题，已由 wyj 当日修复，见 10-12 台账。）

# 第八篇：PPJD/PPXS 播报通道修复与 lark-cli wrapper 隔离机制（10-14）

本篇覆盖 10-14 三个问题：新实例过程播报不显示的根因与修复、lark-cli 的身份归属与配置路径、wrapper 隔离机制的原理与推广。

## 一、PPJD/PPXS 为什么没有过程播报（三层原因，全部修复）

### 1.1 现象与结论

阿祖与 PPJD main 在飞书直聊时看不到过程播报。排查结论：**AGENTS.md 的强制播报规则完整在位**（第 1 次工具调用前必须播报、独立消息兜底等条款都在），agent 一直"认为自己在播报"，但播报通道是坏的——中间文字发不出去，任务完成后随最终答案一次性出现。

### 1.2 三层原因

| 层 | 问题 | 后果 |
|-|-|-|
| ① wrapper HOME 硬编码 XMT（主因） | PPJD/PPXS 克隆自 XMT，`agents/main/lark-cli` 里 `export HOME=/data/agent/openclaw_XMT/...` 没改 | lark-cli 认证失败（not_configured）；ocs_ppjd 去读 XMT 目录报 EACCES；兜底独立播报一条发不出。更严重：就算读通，用的也是 **XMT 的凭据**——正是第零铁律防的身份穿越 |

### 1.3 修复清单（全部验证通过）

4. **AGENTS.md 填真实 chat_id**：PPJD = 阿祖与其直聊（oc_fcfc4553...，从网关日志 received message 线索定位）；PPXS 留占位待首次直聊后固化；
5. **端到端实测**：PPJD 以 bot 身份向阿祖直聊窗口发测试播报，发送成功（message_id 返回 ✓）。

- `not_configured` 先查 **wrapper 的 HOME 指向**——克隆实例必查项；
- "非 JSON 输出"多为 warning 行混在 stdout 前部（如 policy.yml EACCES），从第一个 `{` 开始解析即可；
- lark-cli 配置要写双路径，只写一份会在另一种运行模式下静默失效。

## 二、lark-cli 的身份归属与配置文件路径

### 2.1 PPJD/PPXS 的 lark-cli 用的是谁的身份？

**只有 bot 身份（各自实例的 main-bot 应用机器人），没有绑定任何自然人**（users 数组为空，未做任何人格化授权）。凭据来源是各自 openclaw.json 的 channels.feishu 账户（appId+appSecret）。

**文件完整路径**（每实例两份、内容相同、600 权限、属主=实例用户）：

```
/data/agent/openclaw_PPJD/.openclaw/agents/main/home/.lark-cli/config.json
/data/agent/openclaw_PPJD/.openclaw/agents/main/home/.lark-cli/openclaw/config.json
/data/agent/openclaw_PPXS/.openclaw/agents/main/home/.lark-cli/config.json
/data/agent/openclaw_PPXS/.openclaw/agents/main/home/.lark-cli/openclaw/config.json
```

入口脚本是各实例 `agents/main/lark-cli` wrapper。未绑 user token 意味着这两个实例目前只有 `--as bot` 能力（够播报用）；将来要以某个人身份读文档/发消息需单独做该用户的人格化授权。

### 2.2 为什么"授权是我、chat_id 是我们的会话"，其他用户用 wyj 时仍有过程播报？

因为**主路径与兜底路径是解耦的**：

1. **主路径播报不经过 chat_id**：agent 在工具调用之间输出的文字由 OpenClaw 运行时**自动路由到当前会话的来源窗口**——谁在对话就出现在谁的窗口，与 AGENTS.md 写什么 id 无关，天然对每个用户生效；
2. **兜底播报的规则是"当前会话 chat_id"**：AGENTS.md 写死的 `oc_7005...` 只是它在我们这个窗口的**实例值**。其他用户对话时，每轮运行时上下文带的都是他们的会话 chat_id，正确执行就是替换为当前会话的 id；机器人是所有会话的成员，发谁都通；
3. **授权身份只影响 `--as user` 类动作**（以谁的人格读文档、发消息）；`--as bot` 走应用机器人身份（tenant token），与授权人是谁完全无关。

**边角风险**：若某次执行机械照抄写死的 chat_id 而不看"当前会话"条款，其他用户的任务进度会错发到阿祖的窗口。条款文字能防，但可改为强制措辞："chat_id 必须取本轮运行时上下文的当前会话值，禁止照抄本文示例"（待定）。

## 三、wrapper 的原理：身份环境注入器

### 3.1 它不是 lark-cli，是"改环境 + 换进程"

真正的 lark-cli 是全局唯一一份无状态程序（`/usr/lib/node_modules/@larksuite/cli`），启动时按标准约定找凭据：`$HOME/.lark-cli/` 及 XDG 目录。**lark-cli 的身份不由程序决定，由"它读到了哪个目录下的配置文件"决定**。wrapper 就是利用这一点的每个 agent 专属脚本：

```bash
#!/usr/bin/env bash
export HOME="/data/agent/openclaw_PPJD/.openclaw/agents/main/home"   # ← 全部魔法
export USERPROFILE="…/home"           # Windows 风格兼容
export XDG_CONFIG_HOME="…/home/.config"
export XDG_CACHE_HOME="…/home/.cache"
exec /usr/bin/node /usr/lib/node_modules/@larksuite/cli/scripts/run.js "$@"
```

三个技术点：

1. **`export` 先于 `exec`**：改写环境后 `exec` 用 CLI 进程替换当前 shell（不多余起进程、信号直通、退出码透传），CLI 继承改写后的环境，就会去读**这个 agent 自己的**配置与 token 缓存；
2. **`"$@"` 原样转发**全部参数，stdio 天然继承——对调用方完全透明；
3. **wrapper 不含凭据**，只决定"去哪读凭据"；凭据本体在 home 配置文件里（600）。

### 3.2 为什么能实现实例内多 agent 隔离

| 层 | 机制 | 防什么 |
|-|-|-|
| 逻辑层 | 每 agent 一个 wrapper，各自硬编码**自己的** HOME | 同机同用户下 agent A/B 各读各的配置 |
| 物理层 | 每 agent 一份 `agents/<id>/home/`，属主=实例用户、目录 0700/文件 600 | token 缓存与续期状态物理分开，互不覆盖 |
| 路由层 | 全局 shim `/usr/bin/lark-cli` 按 `OPENCLAW_AGENT_DIR` 转发到对应 agent 的 wrapper | 调用方无需记路径，框架自动选对 wrapper |

路由层的刻意陷阱：shim 在 `OPENCLAW_AGENT_DIR` 缺失时**静默 fallback** 到真实 CLI（按 `$HOME` 落到实例共享槽位）——这就是"跑通 ≠ 身份对"、"永远不要裸跑 lark-cli"铁律的由来（2026-09-16 user token 写进共享槽位事故的根源）。PPJD 的 wrapper 指错家恰好是反面证明：隔离机制立刻把它暴露（not_configured + EACCES）；如果当初"碰巧能用"，就是一次无声的身份穿越。

### 3.3 一次调用的完整信息流转（PPJD main 跑 whoami 为例）

```
① agent 决定调 lark-cli（三选一：export HOME / 直调 wrapper / 注入 OPENCLAW_AGENT_DIR）
② [shim 路径] /usr/bin/lark-cli 读 OPENCLAW_AGENT_DIR=…/agents/main
   → 定位 wrapper …/agents/main/lark-cli → exec 转发
③ wrapper：export HOME=…/agents/main/home（等四变量）→ exec node CLI
④ CLI 读凭据（优先级）：$HOME/.lark-cli/openclaw/config.json（openclaw 上下文）
                       $HOME/.lark-cli/config.json（独立模式）
   内容：appId+appSecret（bot 身份）+ users 列表（user 授权）
⑤ 执行：--as bot → appId+secret 换 tenant_access_token → 应用机器人身份调 API
        --as user → 该 user 的 user_access_token → 自然人身份调 API
⑥ token 缓存读写也在 $HOME 下（cache/）→ 每 agent 的 token 生命周期独立
⑦ 结果原路返回 agent
```

一句话本质：**身份 = 配置文件位置的函数；wrapper 决定位置，所以 wrapper 决定身份。**

### 3.4 推广到 BI 等其他授权：通用公式

**任何"凭据写到可定位路径"的工具，都能用"启动前钉环境/参数"做 per-agent 隔离。** 按凭据定位机制分四类：

| 定位机制 | 隔离手法 | 例 |
|-|-|-|
| 按 `$HOME` | 直接套 wrapper（同款脚本） | lark-cli |
| 按 `XDG_*` | wrapper 加几行 XDG export | 多数遵循规范的 CLI |
| 按专用环境变量 | 包一层"export 变量 + exec"启动器 | **数仓 MCP**：MCP_TOKEN_CACHE_DIR 指向哪、token 落哪、身份就是谁（实例级已实现；agent 级=多 server 条目 + per-agent tool policy，见第七篇） |
| 按 `--config` 参数 | 约定显式传参，或包一层注入默认参数的启动器 | 支持 config 路径的工具 |

应用到 aba / datadev / watcher：先探明凭据落点（不确定只跑 `--help`/只读命令，不贸然写凭据），按表对号入座；凭据目录统一 `workspaces/<agent>/creds/`，0700/600，跑完必验身份。

**两个边界**：

1. wrapper 解决"凭据落点"，**不解决账号授权本身**——user 授权（CAS/OAuth 人格化）每个 agent 仍需各自走流程，且必须在实例用户身份下执行（2026-10-12 GTM root 属主事故：root 代跑授权把令牌写成 root，网关反而读不了）；
2. 硬编码路径/全局单例的工具无法隔离（凭据写死 /etc 或程序目录的），只能改用支持配置路径的调用方式或向工具方提需求。

wrapper 不只是"播报通道"，而是**整个 per-agent 身份体系的路由中枢**——它指错家，所有授权类操作都会跟着穿越。

## 一、问题一：Excel 上传 413——真拦截层在第五层（10-23）

### 1.1 症状

- 商家购买与库存上传（`/api/import/upload-pair`，两文件合计 27.7MB）：预览失败，旧数据未改变，请求失败（413）；
- 卖场业绩上传（`/api/sales-import/upload`，1.55MB）：请求失败。

### 1.2 第一轮（上午）：nginx 默认 1MB 限制

- 证据：nginx error.log 明确记录 client intended to send too large body: 27687531 / 1549994 bytes——请求根本没到后端；
- 修复：`/etc/nginx/sites-available/openclaw-bot-review` 的 `/mallcustomer-board/` 段加 client_max_body_size 200m 与 proxy_read_timeout 300s（备份 .bak-20261023-413），nginx -t 通过后 reload；
- 验证：30MB 打 upload-pair → 401（穿过 nginx 到达后端登录校验层 = 体积放行）；1.6MB multipart 打卖场业绩接口，三层逐层测（nginx → vite 4174 → FastAPI 8000）全部 401。卖场业绩上传当日恢复（confirm 200 实证）。

### 1.3 第二轮（午后）：大文件仍 413，真凶是 WAF

修复后 27.7MB 仍失败，新证据链：

1. 本机 nginx 再无任何 413 记录；用户 4 次重试在源站 access.log 全是 **499 + 0 字节响应**（连接被前置层中途掐断）；
2. 域名 CNAME 指向 yundunwaf2.com（阿里云盾 WAF，47.110.175.59）：https 在 WAF 终结，回源为纯 HTTP 到本机 80；
3. 服务器侧穿 WAF 直测：小请求能过；大 body（3MB/28MB、带浏览器头）直接连接重置，到不了源站。

结论：WAF 层有自己的请求体上限（常见默认约 10MB），27.7MB 合计 body 超限被 WAF 拦截并直接对浏览器回 413。服务器侧无解，需 WAF 控制台调整。

### 1.4 完整链路与排查方法论

五层链路：浏览器 → 阿里云盾 WAF → nginx:80 → vite:4174 → FastAPI:8000。第一轮修复只覆盖了后四层。

方法论沉淀：

- 查 413/超时类问题先画全链路再动手，**每一层都要有独立的到达证据**（error.log 的 413 记录、access.log 的状态码、连接重置三者在不同层出现含义不同）；
- 源站看到 499（客户端断开）+ 0 字节，说明断开发生在更前面的层，别再盯着源站修；
- nginx reload 后旧 worker 短窗内可能仍按旧配置拒绝，验证需重试确认。

### 1.5 解决方案（待 WAF 控制台操作）

| 方案 | 操作 |
|-|-|
| ① 调 WAF 请求体上限（推荐） | 阿里云 WAF 控制台对该域名把请求体大小上限调到 100MB+ |
| ② 路径放行规则 | 对 `/mallcustomer-board/api/*` 配精确放行（部分版本 body 上限不受白名单影响，需试） |
| ③ 临时绕过 | 拆文件分次上传（单文件小于 WAF 限额大概率可过） |

## 三、当日机制答疑沉淀

### 3.1 任务中断如何保存状态并续跑（四层机制）

转录层（每步实时落会话库，恢复时可见断点现场，但被中断的输入不自动重放，需一条新消息触发恢复）→ 文件层（memory 日记边做边写关键节点；脚本自记日志回执）→ 后台层（会切断自身会话的长任务交给脱离会话的脚本执行，内置完成自动播报与 pid 修正；同类还有 automations 与子会话）→ 恢复层（幂等核验：pid 文件、配置回读、日志尾部、接口实测，用磁盘证据重建事实，不信记忆）。

### 3.2 memory 体系分层（日记 / 长期记忆 / 做梦 / 梦日记）

- `memory/YYYY-MM-DD.md` = 日记（原始流水，只增不改）；MEMORY.md = 长期记忆（蒸馏结论，仅主会话加载，群聊禁载防泄漏，有淘汰机制）；
- `memory/dreaming/` = 做梦系统分阶段报告，每晚 03:00 自动扫描（light 浅睡汇集短期候选 → REM 反思主题 → deep 打分晋升，deep 是唯一写 MEMORY.md 的阶段）；三道晋升门槛 minScore/minRecallCount/minUniqueQueries 全过才候选；
- DREAMS.md = 人类可读的梦日记（每晚模型生成的叙事），**不是记忆来源**——防止梦见的内容被当成真实记忆再学一遍；被召回过的片段也会打标剔除，不重复晋升；
- deep 打分权重：相关性 0.30 / 频次 0.24 / 查询多样性 0.15 / 新鲜度 0.15 / 跨天复现 0.10 / 概念密度 0.06；改写 MEMORY.md 前先存快照，最多动旧条目 25%。

### 3.3 为什么改 openclaw.json 能启动功能

功能代码全部内置在 openclaw 包里（/opt/openclaw），配置只是声明式开关与参数，不是功能本身。流程：gateway 启动读配置 → 严格 Schema 校验（配错键整单拒绝，如 Unrecognized key "list"）→ 按 plugins.entries 逐个激活插件并喂配置段 → 插件自行注册运行件（memory-core 激活时自动建 03:00 的做梦 cron 即此机制）→ watcher 热加载后续配置变更（.env 等进程级数据除外，必须重启——GYL 的 aliyun key 事件就是这原理）。

### 3.4 一个 80 端口为什么能挂两个应用

80 端口只属于 nginx 一个进程，两个应用不直接对外；nginx 按 URL 路径前缀分流（`/openclaw-bot-dashboard/` → 127.0.0.1:3000，`/mallcustomer-board/` → 127.0.0.1:4174），能挂多少应用取决于路径前缀数量，与端口数无关。https 由 WAF 终结后以纯 HTTP 回源；内部应用只绑 127.0.0.1，公网不可达。子路径挂载的代价：前端构建须烧入 basePath（Next.js 构建期 env）/ base（vite），代理层须剥前缀（vite proxy rewrite），后端代码才能完全不感知子路径。
