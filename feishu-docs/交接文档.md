### 2.3 为什么"每组建实例"而不是"每组建独立 OpenClaw"

共享的是越共享越值钱的东西（版本、技能库、监控、运维知识），隔离的是越隔离越安全的东西（凭据、数据、进程）：

- **一次升级全舰队生效**：核心统一更新，无版本漂移；
- **一次开发全舰队复用**：门禁插件、蒸馏 skill、规则模板均为一份开发多实例铺开，运维杠杆率 = 实例数 × 1 份工作量；
- **天然全局监控**：看板直读同宿主各实例 sqlite，一张看板覆盖全部；
- **新组分钟级接入**：建用户 + 复制实例模板 + 注册端口；
- 代价（诚实账单）：宿主单点、升级同步爆炸（无法按组灰度）、noisy neighbor、root 被攻破则全部暴露。若出现不同信任域/合规物理隔离/资源互扰等信号，再考虑拆独立部署。

## 三、lark-cli 授权隔离实现

### 3.1 原则（第零铁律）

一切需要认证的操作，凭据只落**本 agent 专属目录**，禁止落到实例级共享槽位或任何他人/其它 agent 的目录；每次执行三步：锁身份（HOME/环境变量指向专属目录）→ 不裸跑 → 跑完 `whoami` 自检（显示别人的名字立即停手）。

### 3.2 实现机制

1. **per-agent HOME 槽位**：`.openclaw/agents/<agentId>/home/.lark-cli`——每个 agent 的飞书凭据（app 凭据 + user token）物理隔离；
2. **三变量环境锚定**：`OPENCLAW_AGENT_ID` + `OPENCLAW_AGENT_DIR` + `LARK_BROKER_SUBJECT` 由 wrapper 脚本固定导出；裸跑全局 lark-cli 会按 \$HOME 静默 fallback 到共享槽位——**命令跑通 ≠ 身份对**，必须以 whoami 输出为准；
3. **双配置路径**：`.lark-cli/config.json`（独立模式，裸跑读取）与 `.lark-cli/openclaw/config.json`（openclaw 上下文运行时读取）是两份文件，绑定/改凭据必须写到运行时读取的那份（教训：config init 只写独立路径，需手工镜像到 openclaw 路径）；
4. **user 身份授权分离**：`--as user` 走各自完成设备码授权的 user token（`lark-cli auth login --scope "..."`），scope 不足按 CLI 提示补授权，禁止借用他人账号或跨 agent 共用授权。

### 3.3 应用级身份：实例 bot 应用独立

每个实例的 bot 身份来自独立飞书应用（如 TeamS 主应用 cli_aa87…、白板 baiban 应用 cli_a934…）。实战案例：data_group 曾误绑主应用，向白板机器人会话发消息报 230002"Bot/User can NOT be out of the chat"——根因是**应用身份与目标会话不匹配**（主应用 bot 不在该群），正解是为它绑定 baiban 应用凭据（`config init --app-id <id> --app-secret-stdin --force-init` + 镜像到运行时路径）。

## 四、用户账号隔离实现（per-user 网关）

### 4.1 机制

每个业务实例创建专属系统用户（ocs\_<组名>），**网关进程以该用户运行**——该实例全部 agent 的所有文件操作（读/写/执行）都以这个 uid 落地。Unix 文件权限即 OS 级隔离：跨实例写入被内核直接拒绝（uid 不匹配），无需容器。

### 4.2 隔离效果

- **写隔离（已生效）**：实例目录属主 = 运行用户（如 ocs_gtm:ocs_gtm），其他实例用户写不进；
- **共享读（显式授权）**：公共资源按白名单放开——`/data/knowledge`（蒸馏日报原料）用 `chmod -R a+rX` 全局可读+目录可遍历、不给写。教训：2026-10-08 该目录缺执行位 x，非 root 实例用户进不了目录，四实例蒸馏空跑，修复后重跑即恢复；
- **管理面分层**：TeamS 与 sxs 两个管理实例保留 root（跨实例运维：systemctl、全局权限、互相派单），业务面一律降权——命令能力削减（无法 systemctl/chmod 全局）是隔离的定价而非缺陷；
- **残余边界**：/tmp 全机共享（粘滞位只防互删）、localhost 互达（网关 API 有 token 鉴权）、系统资源不隔离。

## 五、强制播报实现（broadcast-gate 网关插件）

### 5.1 为什么需要

"长任务必须向用户群发过程播报"的规则写入 AGENTS.md（每 run 注入 system prompt）后，两轮全量核查显示执行率仅约 50% 且"优等生也会退步"——**提示词是软约束**（只是上下文里的 token，靠注意力被看见，长任务中自然衰减）。要成为保证，必须卡在执行层。

### 5.2 机制：before_tool_call 钩子

broadcast-gate 插件通过 `api.on("before_tool_call", handler)` 注册钩子，运行在**模型请求工具与网关真正执行之间**（唯一物理卡点），按 runId 维护状态机：

```
模型调工具 → 钩子检查本 run 播报状态
  ├─ 本轮首个工具调用前未播报 → {block:true, reason:"PROGRESS_BROADCAST_REQUIRED…"}
  ├─ 已播报但静默超 5 分钟（staleMinutes 可配）→ {block:true, reason:"MILESTONE_STALE…"}
  └─ 合规 → 放行
```

### 5.3 弹回-自愈闭环（零人工）

```
调用被拦截 → blockReason 文本作为"工具执行错误"注入模型上下文
  → 模型下一轮读到补救指引（含标准播报命令模板）
  → 执行播报 → 钩子识别为播报调用、更新状态机
  → 重试原工具调用 → 放行 → 任务继续
```

实战数据：铺开以来 17 条弹回记录全部自愈，零任务卡死、零人工干预。

### 5.4 部署要点

`openclaw plugins install --link <目录> --force --accept-capabilities`；配置必须嵌套在 `plugins.entries.broadcast-gate.config`（mode: log 试跑/enforce 强制、staleMinutes、logFile 审计日志）；豁免判定按 sessionKey（cron 触发/子 agent/心跳会话不门禁，防御式：字段缺失放行）。

## 六、晨间知识蒸馏原理与机制

### 6.1 三层链路

```
第1层 原始流水  /data/knowledge/agent-daily-report/<实例>/<agent>/<日期>.md
               （review-furnace 每日 03:30-05:15 从各 agent 会话库自动生成，只增不删）
                    ↓ 每实例 main 的 06:30 cron（isolated 静默）执行 morning-knowledge-distill skill
第2层 知识正文  knowledge/lessons-YYYY-MM.md（坑→根因→解法→适用条件，按月滚动）
      + 索引    knowledge/INDEX.md（行式：编号|一句话标题|标签|次数|最近日期）
                    ↓ 次数≥3 且非【待考】的条目自动升格
第3层 长期记忆  main 的 MEMORY.md「业务知识（自动蒸馏）」单行指针（每个 run 注入上下文）
      + 审计    knowledge/promotion-log.md（时间|编号|动作）
```

设计逻辑是上下文经济学：索引（约 2KB）常驻供扫目录，lessons 正文按需打开，日报流水只在审计时回看——知识无限积累而上下文成本恒定。

### 6.2 skill 六步流程与质量红线

①定参数（实例/昨日/日报目录，glob 空则静默结束）→ ②通读全部日报提取候选（只收"报错→根因→解法→适用条件"与关键业务事实）→ ③查重合并（指纹=日期+agent+标题关键词；同坑追加证据不新增）→ ④写入 lessons+INDEX（格式硬约束：行式五字段，2026-10-12 五实例统一，禁 Markdown 表格变体）→ ⑤静默升格 → ⑥一行统计汇报。

红线：日报写"素材未载明/疑似"的一律标【待考】不编造；幂等（同日重跑不重复）；单日新增>10 条只留最完整的 10 条。

### 6.3 升格机制与护栏

候选 = INDEX 中次数≥3 且非待考；向 main 的 MEMORY.md 追加单行指针（每 run 自动注入，main 遇相似问题即被"看见"）。护栏：升格前与 MEMORY 全文查重、单次最多 2 条、section 超 30 行熔断、promotion-log 全程留痕。

### 6.4 现状（2026-10-12）

五实例全覆盖（TeamS/GTM/GYL/PJT/QD），累计知识 **136 条**（TeamS 60/GTM 33/QD 21/PJT 13/GYL 9），已升格 **5 条**——TeamS 3 条（Codex 产出以落盘产物为准；长任务竞态以 ps 实际进程为准；重复播报归因先查 cron 注册表）、QD 2 条（长任务输出必须落日志；重跑前查旧进程）。典型闭环：TeamS 晨会双发从事故报告（10-07）→ 注册表实锤（10-08）→ 方案落地（10-10）→ 升格进长期记忆（10-11），全程 4 天无人工干预。

## 七、集群健康审查机制（ops/health 自动探针）

> 2026-10-19 上线，是 QD 实例磁盘 100%（SQLite errcode=13）停机事故的直接产物。目标：实例故障从"用户报障才知道"变为"5 分钟内发现、常见故障自动恢复、全程留痕可审计"。

### 7.1 设计原则

- **监控独立于被监控对象**：探针跑在 root crontab（每 5 分钟），刻意不放网关定时任务——网关死时监控必须还活着；
- **状态变化才告警**：同一异常持续存在不重复轰炸（状态机去重），事件与处置双账本全程留痕（events.jsonl / remediation.jsonl）；
- **自动处置白名单化**：只自动执行 operator 人工验证过、无业务判断的操作（重启/清盘），有副作用的（换 key、改配置）只告警等批准。

### 7.2 检查项与阈值

| 检查项 | 判定 | 自动处置 |
|-|-|-|
| 磁盘水位 | ≥85% warn / ≥90% P2 / ≥95% P1 | ≥90% 自动清盘（journal 2 天 + apt + npm + 各实例包缓存，实测约释放 2.1G） |
| 网关存活 | 端口 LISTEN + 进程存活（对照实例端口表） | 实例宕机 → 自动批量拉起（幂等，只拉已死的） |
| 进程僵死 | 进程活但端口不开，连续 2 轮 | 第 2 轮自动重启该实例 |
| 飞书通道 | 网关日志 30 分钟无活动 且 无出站 443 连接 | 仅告警 |
| 错误突变 | 近 5 分钟错误数 ≥ 前 1 小时基线 5 倍且 ≥5 条；磁盘类错误（库满/权限）≥2 条直接 P1 | 告警（30 分钟去重） |
| 响应静默 | 收到用户消息后 120 秒无派发完成 | 告警 |
| 用户重试 | 同一用户 25 秒\~15 分钟内重发相同内容且期间无成功回复 | 直接 P1（四条件全过才报，防飞书重复投递误报） |

### 7.3 处置动作分级

- **T0 自动执行**：R1 实例拉起、R2 磁盘清盘、R3 看板重启、R4 僵死重启（全部无业务判断、可幂等重跑）；
- **T1 人工批准**：换模型 key、重置会话、改配置文件等有副作用的操作——探针只推告警卡片，等 operator 确认；
- **熔断护栏**：同一实例 1 小时内自动重启 ≥2 次即停自动、转人工，防止自动重启掩盖持续崩溃（crash loop）。

### 7.4 通知与审计

告警直接推阿祖飞书会话（单轮上限 3 条 + 幂等键防重复）；全部事件写入 `events.jsonl`、自动处置写入 `remediation.jsonl`，事后可完整复盘"什么时候发现了什么、做了什么、多久恢复"。手动巡检入口：`bash /data/agent/ops/health/health-probe.sh`（健康态输出 events=0）。

### 7.5 实战效果（上线至 2026-10-21）

- 10-19 两次实例短暂离线（14:49 / 14:51）均自动拉起，恢复时长 <1 分钟，飞书消息由重连补收零丢失；
- 磁盘水位多次触发 ≥90% 自动清盘，避免二次 SQLITE_FULL 停机；
- 累计事件 32 条全部留痕，误报（如飞书秒级重复投递被判为"用户重试"）经规则迭代后已归零。

### 7.6 运维入口速查

| 场景 | 操作 |
|-|-|
| 手动巡检一轮 | `bash /data/agent/ops/health/health-probe.sh` |
| 看最近事件/处置 | `tail /data/agent/ops/health/events.jsonl` / `remediation.jsonl` |
| 清盘后仍 ≥95% | 转《实例磁盘满恢复》手册（恢复手册），并评估云盘扩容 |
| 调整阈值/处置动作 | 改 `ops/health/health-probe.sh` 前先备份，改完手动跑健康态确认 0 事件 |

## 八、openclaw-bot-dashboard 监控看板

全集群 OpenClaw 实例的统一监控与运维看板。访问入口：[https://ai-jingfen-server.apps.dashuichangliu.com/openclaw-bot-dashboard](https://ai-jingfen-server.apps.dashuichangliu.com/openclaw-bot-dashboard)。部署于 Furnace 服务器：代码仓库 /data/opt/OpenClaw-bot-review-furnace（Next.js），由 systemd 服务 openclaw-bot-review 托管。

核心特性是**直读数据、无需各实例配合**：看板直接读取各实例的 sqlite 文件与 openclaw.json（Token 消耗取自各 agent 的 openclaw-agent.sqlite，定时任务状态取自实例 state 库的 cron_jobs 表），并配内存 SWR + 落盘两级缓存（Token 统计分钟级、任务状态 60 秒级新鲜度）。因此即使某实例网关宕机，其历史数据与统计依然完整可查。

### 8.1 监控与分析

- **机器人总览** — 卡片墙展示所有 Agent 的名称、Emoji、模型、平台绑定、会话统计和 Gateway 健康状态；
- **全局概况** — 本周 Token 消耗排行榜（Top 10 Agent，支持按实例筛选）；套餐额度水位（按 Key 池聚合的 5 小时额度 + 周额度双进度条，含下次重置时间）；全局统计趋势（Input/Output Token 曲线、平均响应时间，支持按天/周/月/总计切换）；
- **今日播报** — 全集群定时任务三档状态追踪（已完成 / 暂失败 / 待开始，30 秒自刷新）；今日失败任务明细（任务名、所属 Agent 与实例、连续失败次数、错误摘要、时间）；底部 Agent 任务追踪模块按 Agent 分组展示子任务与长期定时任务明细；
- **Agent 日报** — 每日定时聚合各 Agent 会话事实（会话数、任务列表、工具调用、定时任务四项统计），由 LLM 总结生成结构化日报（主要任务、问题与修复等分节）；按实例分组浏览，支持一键重新生成；
- **消息统计** — Token 消耗和平均响应时间趋势，支持按天/周/月查看，SVG 图表展示。

### 8.2 集群管理操作

- **API Keys** — 实例级密钥池管理：按实例 Tab 切换、点选式更换 Key（写入 auth profile 并热重载生效）；Key 池总览按指纹聚合展示共用同一 Key 的全部 Agent；明文 Key 仅服务端注册表保管，浏览器全程不接触；
- **模型列表** — 查看所有已配置的 Provider 和模型（上下文窗口、最大输出、推理支持），支持单模型测试；
- **会话管理** — 按 Agent 浏览所有会话，自动识别类型（私聊、群聊、定时任务），含 Token 用量与连通性测试；
- **技能管理** — 查看所有已安装技能（内置、扩展、自定义），支持搜索和筛选；
- **告警中心** — 配置告警规则（模型不可用、机器人无响应），通过飞书发送通知。
