# 平台架构详解 — 设计决策与前因后果

> 本文回答一个问题：这套平台为什么长成现在这个样子。
> 所有决策都对应真实生产事故或明确的运营痛点，无一条是"理论上应该"。

## 1. 总体拓扑：一台宿主机 → 10 实例 → 30+ Agent

**起点（2026-08）**：单实例承载全部业务。问题很快出现：配置互相污染、一个业务的调试影响其他业务的 Agent、无法按业务线管理技能与凭据。

**决策**：按业务线拆 10 个实例（GTM/GYL/need/PJT/PPJD/PPXS/QD/sxs/TeamS/XMT），每实例独立网关进程 + 配置 + 状态库 + 凭据。

**代价与收益**：
- 代价：10 个网关进程的运维复杂度 → 由 `ops/` 编排体系（端口注册表、健康等待、降权拉起）消化
- 收益：故障域隔离（单实例崩溃不蔓延）、权限隔离（每实例专属系统用户）、管理粒度（按业务线发技能/配机器人）

**为什么实例内还要再拆子 Agent**：同一业务线内不同职能（如"吴英杰的助手"vs"靳文慧的助手"）需要独立的记忆、技能集合与飞书身份。实例=资源与安全边界，Agent=身份与上下文边界。

## 2. 凭据治理：从"约定"到"基础设施"

演进路径（每步都是被事故推着走的）：

1. **裸用 lark-cli** → 2026-09-16 串号事故：子 agent 在群聊用错身份发言。根因：凭据可被自由访问、无审计，LLM 在长任务中会抄近路。
2. **wrapper（每 agent 独立启动脚本）**：解决"凭据放哪"——HOME 隔离到 `agents/<id>/home/`。但 wrapper 防不了"以谁的身份"这种静默错配，也没有审计。
3. **lark-broker（集中代理）**：跨身份任务链必须显式声明身份（`LARK_BROKER_SUBJECT`），broker 校验白名单→查命令族→写审计→转发。串身份从"静默事故"变成"当场拒绝+有据可查"。
4. **制度固化**：AGENTS.md 第零铁律 + users.json 黑名单 + 定时任务链全部走 broker。

**核心认知**：wrapper 是门锁，broker 是带日志的门禁系统。对人类，制度约束行为；对 LLM，只有基础设施能约束行为。

## 3. 行为治理：播报门禁的三版演进

**问题**：Agent 长任务对用户静默（跑 10 分钟一句话不说），或结束后刷屏。

1. **v1 提示词规范**（AGENTS.md 播报条款）：有效但不稳定——模型偶尔漏播报，无法保证 100%。
2. **v2 独立消息兜底**（09-17）：发现飞书流式卡片存在不刷新缺陷，规定凡调工具的任务必须用 lark-cli 发独立消息兜底。
3. **v3 broadcast-gate 网关插件**（09-18 起）：`before_tool_call` 钩子上强制——首调工具前未播报→弹回；距上次播报超 5 分钟→弹回。弹回信息内嵌补救指令，模型自动补播报后重试。**把"希望它播报"变成"不播报就干不了活"**。

**为什么先 log 模式再 enforce**：门禁本身可能误拦（比如拿不到 sessionKey 的边缘场景）。先观察违规日志的误拦率，再切强制——治理组件自身也要有灰度。

## 4. 自动化设计：确定性优先

**日报链路的两条平行路径**：

- **定时主链**（每天 04:20/05:20 准点）：冻结 shell 命令，`payload.kind=command`，全程零模型参与。身份、配置、日志路径在创建任务时就焊死在命令行里。
- **交互补报**（用户聊天里说"补个日报"）：模型读 SKILL.md，拼命令执行——这条路径才需要文档。

**为什么主链不用模型**：一条日报要执行几十次飞书调用，模型参与每次调用=几十次抄近路的机会。冻结命令把模型的自由度压缩到"声明身份"那一次。**LLM 环境的可靠性不是让模型每次都做对，而是让它没机会做错。**

**翻车案例**：SKILL.md 比 broker 机制早一周写就，之后没更新——文档滞后导致交互补报路径与实际代码脱节。教训：文档服务交互路径，代码即主链文档，两者变更必须同步。

## 5. 知识体系：经验不过夜

三层记忆 + 一条蒸馏管线：

```
每日 memory/YYYY-MM-DD.md（原始日志，所有踩坑与解法）
        │ morning-knowledge-distill（夜间定时）
        ▼
每日 lessons（结构化知识 + INDEX 索引）──→ 喂回 agent 上下文
        │
        ▼ 高频/通用化的沉淀为技能（skills/ops/*）
```

**原则**：每个真实故障的处理过程，要么沉淀为技能（可复用 playbook），要么写进 AGENTS.md（制度性教训），要么进 lessons 知识库（背景知识）。不沉淀 = 同样的坑付两次学费。

## 6. 可观测性：从黑盒到可运营

- **review-furnace 看板**（姊妹仓库 openclaw-bot-dashboard）：全员使用量、token 消耗排行、定时任务三档状态、模型/Key 管理、套餐水位——运营视角一张页
- **agent-broadcast-audit 技能**：播报合规率统计（应播报任务中实际播报的比例）——这是对 LLM 行为的 evals，不是普通日志监控
- **multi-instance-cron-audit 技能**："任意时间窗内某 Agent 干了什么"的行为取证

**管理层视角**：AI 落地要能回答"用了多少、省了多少、出过什么事"。这三样分别由看板、日报体系、审计日志支撑。

## 7. 如果重新来一次，会改的三件事

1. **第一天就上 broker**：串号事故本可避免，凭据治理越早越省
2. **端口注册表与 config 单一真源**：端口漂移排查耗过 70 分钟，应一开始就强制以注册表为准（config 里 port 字段干脆删掉）
3. **SKILL.md 与主链代码同仓同评审**：文档滞后 38 天才被发现，说明"旁路文档"没有变更纪律——应纳入同一提交
